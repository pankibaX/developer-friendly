Chunk Architecture & Transactions Question 1 of 20
📌 1. Concept Covered
The architectural dichotomy between Chunk-Oriented Processing (<I, O>chunk) and Tasklets, transaction scope, commit intervals, and partial failure isolation.
❓ 2. Question
A developer built a batch step to process 500,000 billing records. Instead of chunk processing, they implemented a Tasklet with an in-memory loop. In production, processing record #498,200 throws a DB constraint exception. The entire job crashes, rolling back all 498,199 previously processed records! Why did this happen, and how does Chunk-oriented processing solve this with commit intervals?
💻 3. Code Challenge
public class BillingTasklet implements Tasklet { @Autowired private AccountRepository accountRepo; @Autowired private BillingService billingService; @Override @Transactional // Executes entire loop in ONE single transaction public RepeatStatus execute(StepContribution contribution, ChunkContext chunkContext) { List<Account> accounts = accountRepo.findAll(); // OOM Hazard! for (Account account : accounts) { billingService.processBill(account); // Fails at record 498,200 -> ALL 500k rollback! } return RepeatStatus.FINISHED; } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

1. WHAT is the problem & architecture:
The developer attempted to process 500,000 items inside a single Tasklet. In Spring Batch, a Tasklet is designed as a single, indivisible unit of work (e.g. running an archive script, clearing a directory, executing a DDL statement). Wrapping 500,000 items in a Tasklet executes them inside one single monolithic transaction, causing memory exhaustion and catastrophic total rollback upon any single item failure.

2. WHY this occurs under the hood:

  • Tasklet Transaction Boundary: A Tasklet executes inside a single transaction. If record #498,200 throws an unhandled runtime exception, the transaction manager marks the entire transaction for rollback. Hours of processing and 498,199 records are completely discarded.
  • Heap Exhaustion (OOM): Calling findAll() loads all 500,000 entities into the JVM heap simultaneously, overwhelming Eden/Old Gen and triggering GC death spirals.
  • Chunk Architecture Solution: Chunk processing decouples ingestion, business logic, and persistence into discrete cycles of commitInterval (e.g., 1,000 items). Spring Batch opens a transaction, reads 1,000 items one-by-one via ItemReader, transforms them one-by-one via ItemProcessor, flushes all 1,000 items to DB via ItemWriter.write(Chunk), commits the transaction, and persists checkpoint metadata in BATCH_STEP_EXECUTION. If chunk #499 fails, chunks #1 through #498 remain safely committed!

3. HOW to implement the production pattern:

Production Fix: Chunk-Oriented Step Configuration (Spring Batch 5)Java
@Bean
public Step billingChunkStep(JobRepository jobRepository, 
                            PlatformTransactionManager transactionManager,
                            ItemReader<Account> accountReader,
                            ItemProcessor<Account, Bill> billingProcessor,
                            ItemWriter<Bill> billWriter) {
    return new StepBuilder("billingChunkStep", jobRepository)
        .<Account, Bill>chunk(1000, transactionManager) // Chunk commit interval = 1,000
        .reader(accountReader)
        .processor(billingProcessor)
        .writer(billWriter)
        .build();
}

4. Deep Architectural Probes:

  • How to choose commitInterval: If commitInterval is too small (e.g., 10), JDBC transaction commit overhead and network roundtrips dominate runtime. If too large (e.g., 50,000), DB undo log/redo log fills up, row locks are held for long durations, and rollbacks are expensive. Standard enterprise sweet spot is between 500 and 2,500.
  • Tasklet Best Practice: Reserve Tasklets strictly for administrative step setup (e.g. validating incoming file existence, staging tables, unzipping payloads) or post-batch cleanup (e.g. archiving processed files, dropping temp tables).

5. Quick Interview Study Cheat-Sheet:

  • Tasklet: 1 step = 1 execution = 1 transaction. Great for file management, cleanup, or Stored Procedure calls.
  • Chunk: Read 1-by-1 → Process 1-by-1 → Write in batch of N. Each chunk has its own isolated transaction boundary.
  • Resilience: Chunk processing enables checkpointing, restartability, skip, and retry.

Item Readers & DB Streaming Question 2 of 20
📌 1. Concept Covered
Memory footprint, connection holding, and thread-safety differences between JdbcCursorItemReader (streaming cursor) and JdbcPagingItemReader (keyset/offset pagination).
❓ 2. Question
An architect used JdbcCursorItemReader to read 20,000,000 rows. When running in a multi-threaded step with 8 threads, the job produces missing rows, duplicate records, and randomly crashes with SQLException: Connection is closed or socket timeouts. Why is JdbcCursorItemReader failing, and when should you switch to JdbcPagingItemReader?
💻 3. Code Challenge
@Bean public JdbcCursorItemReader<Customer> customerCursorReader(DataSource dataSource) { JdbcCursorItemReader<Customer> reader = new JdbcCursorItemReader<>(); reader.setDataSource(dataSource); reader.setSql("SELECT id, name, balance FROM customers ORDER BY id"); reader.setRowMapper(new CustomerRowMapper()); reader.setFetchSize(1000); // CRITICAL: Used directly inside a multi-threaded Step! return reader; }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

1. WHAT is the problem & architecture:
JdbcCursorItemReader is strictly NOT thread-safe. It holds a single open java.sql.Connection and an open cursor (ResultSet) throughout the entire lifetime of the step. Running it concurrently across multiple worker threads corrupts the internal row pointer, while network load balancers or DB firewalls terminate the connection if idle during slow processor stages.

2. WHY this occurs under the hood:

  • Stateful Cursor: JdbcCursorItemReader calls ResultSet.next() sequentially. Under multi-threading, multiple threads invoke next() simultaneously without synchronization, causing missed rows, concurrent read collisions, and corrupted state.
  • Connection Pinning & Firewalls: Holding one connection open for hours while slow chunks process triggers DB idle timeouts, TCP resets, or firewall drops (Connection reset by peer).
  • JdbcPagingItemReader Mechanics: In contrast, JdbcPagingItemReader fetches data in discrete chunks called pages (e.g., 1,000 rows per page using SQL LIMIT / OFFSET or indexed keyset pagination). It borrows a connection from the pool, reads a page, releases the connection back to the pool, and is fully thread-safe because each page fetch is synchronized.

3. HOW to implement the production pattern:

Production Fix: Thread-Safe JdbcPagingItemReaderJava
@Bean
public JdbcPagingItemReader<Customer> customerPagingReader(
        DataSource dataSource, 
        PagingQueryProvider queryProvider) {
    return new JdbcPagingItemReaderBuilder<Customer>()
        .name("customerPagingReader")
        .dataSource(dataSource)
        .queryProvider(queryProvider)
        .pageSize(1000)
        .rowMapper(new CustomerRowMapper())
        .saveState(false) // Disable state saving if running in multi-threaded steps
        .build();
}

@Bean
public SqlPagingQueryProviderFactoryBean queryProvider(DataSource dataSource) {
    SqlPagingQueryProviderFactoryBean provider = new SqlPagingQueryProviderFactoryBean();
    provider.setDataSource(dataSource);
    provider.setSelectClause("SELECT id, name, balance");
    provider.setFromClause("FROM customers");
    // Sort keys are MANDATORY for paging readers to guarantee deterministic page boundaries!
    provider.setSortKey("id"); 
    return provider;
}

4. Deep Architectural Probes:

  • Mandatory Sort Key: Why does JdbcPagingItemReader require a sort key? Without an unambiguous ORDER BY clause, relational database page slicing is non-deterministic, causing records near page borders to be read twice or skipped completely.
  • SynchronizedItemStreamReader Wrapper: If you must use a cursor reader or flat file reader in a multi-threaded step, wrap it in new SynchronizedItemStreamReader<>(delegateReader) to synchronize the read() method.

5. Quick Interview Study Cheat-Sheet:

  • Cursor Reader: 1 connection, 1 cursor, fastest for single-threaded steps, NOT thread-safe, risks timeout on long runs.
  • Paging Reader: Borrows/returns connections per page, fully thread-safe, uses sort keys, ideal for multi-threaded steps.
  • Multi-threaded caution: Set saveState(false) on paging readers in multi-threaded steps because thread completion order is non-deterministic.

📌 1. Concept Covered

❓ 2. Question
A financial batch job processing 10,000,000 records from a file crashes at record #6,500,000 due to a power outage. When restarted, it does NOT re-read from record 1; instead, it resumes at record #6,500,001. How does Spring Batch track this state across JVM crashes, which metadata tables are involved, and what role does ItemStream.update(ExecutionContext) play?

🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

1. WHAT is the problem & architecture:
Spring Batch provides built-in fault-tolerant restartability backed by its metadata schema. It records job and step execution state in relational tables managed by the JobRepository. The ItemStream contract periodically snapshots cursor offsets into the ExecutionContext at each chunk commit boundary.

2. WHY this occurs under the hood:

  • JobInstance vs JobExecution: BATCH_JOB_INSTANCE defines what to run (e.g. 'payrollJob' with date='2026-10-28'). BATCH_JOB_EXECUTION defines an attempt to run it. If Run #1 fails, its status in BATCH_JOB_EXECUTION is FAILED. When launched again with the same parameters, Spring Batch recognizes the existing JobInstance, sees it was not completed, and launches Run #2 under the same instance.
  • ItemStream Contract: Readers implementing ItemStream implement open(ExecutionContext), update(ExecutionContext), and close(). At every chunk commit (e.g., every 1,000 records), update() writes current.item.count = 6500000 into the step's ExecutionContext, which is serialized to BATCH_STEP_EXECUTION_CONTEXT in the DB within the chunk transaction.
  • Recovery on Restart: Upon restart, Spring Batch calls reader.open(executionContext). The reader inspects executionContext.getInt("current.item.count"), skips the first 6,500,000 lines directly, and emits line 6,500,001!

3. HOW to implement the production pattern:

Production Code: Custom ItemStreamReader with Checkpoint PersistenceJava
public class CheckpointedOrderReader implements ItemStreamReader<Order> {
    private static final String CURRENT_INDEX = "current.order.index";
    private int currentIndex = 0;
    private List<Order> orders;

    @Override
    public Order read() {
        if (currentIndex < orders.size()) {
            return orders.get(currentIndex++);
        }
        return null; // Signals end of stream
    }

    @Override
    public void open(ExecutionContext executionContext) {
        // Restore checkpoint upon job restart
        if (executionContext.containsKey(CURRENT_INDEX)) {
            this.currentIndex = executionContext.getInt(CURRENT_INDEX);
        } else {
            this.currentIndex = 0;
        }
    }

    @Override
    public void update(ExecutionContext executionContext) {
        // Invoked automatically by Spring Batch at each chunk transaction commit!
        executionContext.putInt(CURRENT_INDEX, this.currentIndex);
    }

    @Override
    public void close() {}
}

4. Deep Architectural Probes:

  • What if status is COMPLETED? If a JobInstance already has a successful execution with status COMPLETED in BATCH_JOB_EXECUTION, Spring Batch will throw JobInstanceAlreadyCompleteException and refuse to run. A completed job instance can never be restarted.
  • Transaction Isolation on JobRepository: JobRepository typically uses ISOLATION_SERIALIZABLE or ISOLATION_READ_COMMITTED to prevent phantom reads when multiple step executions update metadata concurrently.

5. Quick Interview Study Cheat-Sheet:

  • BATCH_JOB_INSTANCE: Job name + identifying parameters (defines uniqueness).
  • BATCH_JOB_EXECUTION: Execution attempt status (STARTED, COMPLETED, FAILED).
  • BATCH_STEP_EXECUTION: Step metrics (read_count, write_count, commit_count).
  • BATCH_STEP_EXECUTION_CONTEXT: Serialized state (offsets, line numbers) for restart.
  • ItemStream: open() reads state; update() saves state at chunk commit.

Job Parameters & Instance Identity Question 4 of 20
📌 1. Concept Covered
The relationship between Job Parameters and JobInstance uniqueness, identifying vs non-identifying parameters, and production risks of RunIdIncrementer.
❓ 2. Question
An automated daily settlement job is triggered with JobParametersBuilder.addString("date", "2026-10-28"). The first execution completes successfully. An operator accidentally triggers it again 10 minutes later, and Spring Batch throws JobInstanceAlreadyCompleteException. A junior developer fixes it by adding .incrementer(new RunIdIncrementer()). Why is using RunIdIncrementer dangerous in enterprise financial systems, and how should rerun policies be designed?
💻 3. Code Challenge
@Bean public Job settlementJob(JobRepository jobRepository, Step settlementStep) { return new JobBuilder("settlementJob", jobRepository) // DANGEROUS QUICK FIX: Generates run.id=1, run.id=2, run.id=3... // Every execution creates a BRAND NEW JobInstance! .incrementer(new RunIdIncrementer()) .start(settlementStep) .build(); }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

1. WHAT is the problem & architecture:
In Spring Batch, a JobInstance is defined by Job Name + Identifying Job Parameters. If a job completes with status COMPLETED, Spring Batch prevents re-execution with the same parameters to protect against accidental duplicate processing. Adding RunIdIncrementer injects a synthetic counter (run.id), forcing every invocation into a new JobInstance and completely disabling duplicate execution prevention!

2. WHY this occurs under the hood:

  • Double Settlement Risk: In financial settlement, payroll, or stock trading, running the same date twice could double-bill customers or double-credit payouts. Spring Batch throwing JobInstanceAlreadyCompleteException is a critical safety feature, not a bug!
  • Loss of Restartability: When RunIdIncrementer creates a new JobInstance for every run, if a job fails at record 500,000 and you trigger it again, it starts over from record 1 as a brand-new instance instead of resuming from record 500,001!
  • Non-Identifying Parameters: Since Spring Batch 2.x/5.x, you can pass parameters with identifying = false (e.g. an execution timestamp or trace ID) using addString("timestamp", ts, false). Non-identifying parameters do not affect JobInstance identity.

3. HOW to implement the production pattern:

Production Best Practice: Explicit Parameter Design & Safe RerunsJava
// Triggering code in service/controller
public void launchDailySettlement(LocalDate settlementDate, boolean forceRerun) {
    JobParametersBuilder builder = new JobParametersBuilder();
    
    // Identifying parameter: Business identity of the job (1 execution per day)
    builder.addLocalDate("settlementDate", settlementDate, true);

    // Non-identifying parameter: Audit tracking only, does not alter JobInstance uniqueness
    builder.addLong("triggerTimestamp", System.currentTimeMillis(), false);

    if (forceRerun) {
        // If business explicitly authorizes rerun, add an explicit run-id or rerun counter
        builder.addLong("rerunVersion", System.currentTimeMillis(), true);
    }

    try {
        jobLauncher.run(settlementJob, builder.toJobParameters());
    } catch (JobInstanceAlreadyCompleteException e) {
        log.warn("Job for date {} has ALREADY COMPLETED successfully. Refusing duplicate run.", settlementDate);
        throw new DuplicateBatchExecutionException("Settlement already executed for " + settlementDate);
    }
}

4. Deep Architectural Probes:

  • When is RunIdIncrementer acceptable? It is acceptable in ETL ingestion jobs that must run on a recurring schedule without unique parameters (e.g., polling an SFTP folder every 15 minutes where each run is independent).
  • JobExplorer API: You can query JobExplorer.getJobInstances("settlementJob", 0, 10) to inspect prior executions programmatically before launching.

5. Quick Interview Study Cheat-Sheet:

  • JobInstance: Job Name + Identifying Parameters. Completed instances can NEVER be rerun.
  • RunIdIncrementer Pitfall: Circumvents idempotency guards and breaks step restartability.
  • Non-Identifying Parameters: Pass identifying = false for metadata like traceId or executionTimestamp.

Fault Tolerance & Exception Policies Question 5 of 20
📌 1. Concept Covered
Configuring fault tolerance in Spring Batch: SkipPolicy vs RetryPolicy, handling transient vs permanent exceptions, and preventing catastrophic error masking.
❓ 2. Question
A developer configured fault tolerance on a critical payment processing step using .faultTolerant().skip(Exception.class).skipLimit(100). In production, when the database disk became full (CannotGetJdbcConnectionException), Spring Batch silently skipped the first 100 payments, recorded the step as completed, and dropped 100 customer payments! What went wrong, and how do you configure strict skippable vs non-skippable exception policies?
💻 3. Code Challenge
@Bean public Step paymentStep(JobRepository jobRepository, PlatformTransactionManager txManager) { return new StepBuilder("paymentStep", jobRepository) .<PaymentDto, PaymentEntity>chunk(500, txManager) .reader(paymentReader()) .processor(paymentProcessor()) .writer(paymentWriter()) // DANGEROUS: Catches Exception.class! Skips infrastructure/DB fatal crashes! .faultTolerant() .skip(Exception.class) .skipLimit(100) .build(); }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

1. WHAT is the problem & architecture:
The developer configured .skip(Exception.class), which matches all checked and unchecked exceptions, including fatal infrastructure failures (DB connection pool exhaustion, disk full, out of memory, network failure). Spring Batch treated the first 100 DB crashes as bad records, skipped them, and stopped the job only after reaching 100 skips, leaving data permanently dropped and uncommitted.

2. WHY this occurs under the hood:

  • Skip vs Retry Distinction:
    • Skip: Designed for deterministic, unrecoverable data errors (e.g. malformed CSV format, invalid email string, business validation failure). Retrying would produce the exact same error.
    • Retry: Designed for transient, recoverable infrastructure glitches (e.g. optimistic locking failure, temporary DB network timeout, remote REST 503). Retrying after backoff may succeed.
  • Non-Skippable Exceptions: Fatal infrastructure exceptions (e.g., DataAccessResourceFailureException, TransactionException, OutOfMemoryError) must never be skipped. They must fail the step immediately so alerts trigger and operators can intervene.

3. HOW to implement the production pattern:

Production Solution: Fine-Grained Skip and Retry ConfigurationJava
@Bean
public Step paymentStep(JobRepository jobRepository, PlatformTransactionManager txManager) {
    return new StepBuilder("paymentStep", jobRepository)
        .<PaymentDto, PaymentEntity>chunk(500, txManager)
        .reader(paymentReader())
        .processor(paymentProcessor())
        .writer(paymentWriter())
        .faultTolerant()
        // 1. Skip ONLY deterministic business format errors
        .skip(FlatFileParseException.class)
        .skip(InvalidPaymentDataException.class)
        .skipLimit(50) // Maximum allowable bad rows before failing step
        
        // 2. Explicitly NEVER skip database or infrastructure errors
        .noSkip(DataAccessResourceFailureException.class)
        .noSkip(CannotCreateTransactionException.class)
        
        // 3. Retry transient network/locking glitches with backoff
        .retry(OptimisticLockingFailureException.class)
        .retry(TransientDataAccessException.class)
        .retryLimit(3)
        .backOffPolicy(new ExponentialBackOffPolicy())
        .build();
}

4. Deep Architectural Probes:

  • Custom SkipPolicy: For dynamic business logic, implement SkipPolicy directly: shouldSkip(Throwable t, long skipCount). This allows skipping only if the error threshold represents less than 1% of total read records.
  • Retry Exhaustion: When retryLimit (e.g. 3) is exhausted on a record, what happens? If the exception type is also marked as skippable, it is then skipped; otherwise, the chunk rolls back and the step fails.

5. Quick Interview Study Cheat-Sheet:

  • Skip: For bad data payloads (format error, parsing failure).
  • Retry: For transient network blips or DB deadlocks (with ExponentialBackOff).
  • Rule of thumb: Never use .skip(Exception.class); always whitelist specific exceptions and blacklist fatal DB errors with noSkip().

Listeners & Dead-Letter Auditing Question 6 of 20

❓ 2. Question
When .skip() is enabled, Spring Batch silently skips bad records without breaking the job. public class AuditSkipListener implements ItemSkipListener<CustomerInput, CustomerEntity> { @Autowired private DeadLetterService dlqService; @Override public void onSkipInRead(Throwable t) { // Record skipped during parsing/reading } @Override public void onSkipInProcess(CustomerInput item, Throwable t) { // Record skipped during business transformation } @Override public void onSkipInWrite(CustomerEntity item, Throwable t) { // Record skipped during database insert/update } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

1. WHAT is the problem & architecture:
In enterprise processing, skipping a record cannot mean discarding it into void. Regulators and downstream reconciliation teams require a full audit trail. ItemSkipListener<I, O> provides lifecycle hooks triggered whenever an item is skipped in the read, process, or write phase.

2. WHY this occurs under the hood:

  • Three Skip Phases:
    • onSkipInRead(Throwable t): The item could not even be constructed (e.g. malformed CSV column count, unparseable date). The item itself is null; only the exception is provided.
    • onSkipInProcess(I item, Throwable t): The raw input item is available alongside the validation exception.
    • onSkipInWrite(O item, Throwable t): The transformed output entity failed during SQL batch execution.
  • Transaction Hazard: The listener is called during chunk execution. If the listener tries to save to the database using the same active transaction that is currently rolling back or marked as dirty, the audit save itself will fail! The DLQ/Audit persistence must either run asynchronously or use @Transactional(propagation = Propagation.REQUIRES_NEW).

3. HOW to implement the production pattern:

Production Implementation: Non-Blocking Dead-Letter Audit ListenerJava
@Component
@Slf4j
public class DeadLetterSkipListener implements ItemSkipListener<CustomerInput, CustomerEntity> {

    private final KafkaTemplate<String, DeadLetterEvent> kafkaTemplate;

    public DeadLetterSkipListener(KafkaTemplate<String, DeadLetterEvent> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    @Override
    public void onSkipInRead(Throwable t) {
        log.error("Skip in READ phase: {}", t.getMessage());
        publishDlq("READ_ERROR", null, t);
    }

    @Override
    public void onSkipInProcess(CustomerInput item, Throwable t) {
        log.warn("Skip in PROCESS phase for item {}: {}", item.getCustomerId(), t.getMessage());
        publishDlq("PROCESS_ERROR", item, t);
    }

    @Override
    public void onSkipInWrite(CustomerEntity item, Throwable t) {
        log.error("Skip in WRITE phase for entity {}: {}", item.getId(), t.getMessage());
        publishDlq("WRITE_ERROR", item, t);
    }

    private void publishDlq(String phase, Object payload, Throwable t) {
        DeadLetterEvent event = new DeadLetterEvent(
            phase,
            payload != null ? payload.toString() : "UNREADABLE_RAW_PAYLOAD",
            t.getClass().getSimpleName(),
            t.getMessage(),
            Instant.now()
        );
        // Offload to Kafka DLQ topic (independent of DB transaction!)
        kafkaTemplate.send("batch-dead-letter-topic", event);
    }
}

4. Deep Architectural Probes:

  • StepExecution Notification: You can inject StepExecution to extract stepExecution.getJobExecution().getJobId() and include the exact job run metadata in the dead-letter record.
  • RetryListener: Similarly, RetryListener has open(), close(), and onError() callbacks useful for logging intermittent retry warnings.

5. Quick Interview Study Cheat-Sheet:

  • onSkipInRead: Item is null (parse failure); inspect Throwable.
  • onSkipInProcess: Input item available; validation failure.
  • onSkipInWrite: Output entity available; persistence failure.
  • Transaction safety: Use Kafka DLQ or REQUIRES_NEW for DB audit records.

    private final JobOperator jobOperator;
    private final JobExplorer jobExplorer;

    @PostMapping("/recover-zombie/{executionId}")

        JobExecution execution = jobExplorer.getJobExecution(executionId);
        if (execution == null) {
            return ResponseEntity.notFound().build();
        }

            try {
                // Step 1: Attempt graceful stop
                jobOperator.stop(executionId);
                log.info("Sent stop signal to execution {}", executionId);

                log.warn("Could not stop execution {}: {}. Forcing status update...", executionId, e.getMessage());

            execution.setExitStatus(new ExitStatus("FAILED", "Process killed externally (OOM/Crash)"));
            execution.setEndTime(LocalDateTime.now());

            for (StepExecution stepExecution : execution.getStepExecutions()) {
                if (stepExecution.getStatus() == BatchStatus.STARTED) {
                    stepExecution.setStatus(BatchStatus.FAILED);
                    stepExecution.setExitStatus(new ExitStatus("FAILED", "Parent process killed"));
                    stepExecution.setEndTime(LocalDateTime.now());
                }
            }
        }

        return ResponseEntity.ok("Execution " + executionId + " transitioned to FAILED. Ready for restart.");
    }

  • Removal of Builder Factories: JobBuilderFactory and StepBuilderFactory were thin wrappers around JobRepository. They have been deleted. You now directly instantiate new JobBuilder("jobName", jobRepository) and new StepBuilder("stepName", jobRepository).
  • Mandatory TransactionManager in Chunks: In Batch 4, transaction manager was implicitly passed. In Batch 5, .<I, O>chunk(size, transactionManager) requires the PlatformTransactionManager explicitly passed into the chunk method signature, enforcing explicit transactional governance.

3. HOW to implement the production pattern:

Production Modernization: Idiomatic Spring Batch 5 & Spring Boot 3 ConfigurationJava
package com.company.batch.config;

import org.springframework.batch.core.Job;
import org.springframework.batch.core.Step;
import org.springframework.batch.core.job.builder.JobBuilder;
import org.springframework.batch.core.repository.JobRepository;
import org.springframework.batch.core.step.builder.StepBuilder;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.transaction.PlatformTransactionManager;

@Configuration
// DO NOT ADD @EnableBatchProcessing in Spring Boot 3 unless overriding DefaultBatchConfiguration!
public class ModernBatchConfig {

    @Bean
    public Job customerMigrationJob(JobRepository jobRepository, Step migrationStep) {
        // Modern Spring Batch 5: Explicit JobBuilder with JobRepository
        return new JobBuilder("customerMigrationJob", jobRepository)
            .start(migrationStep)
            .build();
    }

    @Bean
    public Step migrationStep(JobRepository jobRepository, 
                             PlatformTransactionManager transactionManager,
                             ItemReader<Customer> customerReader,
                             ItemWriter<Customer> customerWriter) {
        // Modern Spring Batch 5: Explicit StepBuilder with mandatory TransactionManager in chunk()
        return new StepBuilder("migrationStep", jobRepository)
            .<Customer, Customer>chunk(1000, transactionManager)
            .reader(customerReader)
            .writer(customerWriter)
            .build();
    }
}
