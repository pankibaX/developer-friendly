Answer Key & Deep-Dive Explanation

Part A (The Concurrent In-Flight Check-Then-Act Race):
The implementation suffers from a classic Time-Of-Check to Time-Of-Use (TOCTOU) race condition:
1. Request 1 arrives; findByIdempotencyKey returns empty because nothing is saved yet. It invokes the external gateway.
2. Client socket times out and immediately fires Request 2 with the same key.
3. Request 2 arrives at another pod; Request 1 is still blocked waiting on the gateway, so findByIdempotencyKey ALSO returns empty.
4. Both threads call gateway.executeCharge() concurrently — customer is double-charged! Furthermore, the second database save will either throw a unique constraint violation after charging or overwrite the first transaction.

Part B (Architectural In-Flight State Locking):
• Acquire an atomic distributed lock via Redis SET idempotency:{key} PROCESSING NX EX 120 before processing.
• If key already exists in PROCESSING state: return HTTP 409 Conflict or HTTP 425 Too Early with Retry-After header, informing client request is actively processing.
• Once the transaction completes, update Redis key to COMPLETED storing the serialized response payload with TTL (e.g. 24 hours).
• Subsequent calls return the cached response payload immediately without calling the gateway.

Part C (Payload Tampering & Hash Mismatch):
The idempotency record must store a cryptographic hash (SHA-256) of the original request body alongside the key. If an incoming request matches the key but has a different payload hash, the server must reject it with HTTP 422 Unprocessable Entity or HTTP 400 Bad Request with error IDEMPOTENCY_PAYLOAD_MISMATCH to prevent replay tampering.

@Component
public class DistributedIdempotencyManager {

    @Autowired
    private StringRedisTemplate redisTemplate;

    public IdempotencyLock acquireLock(String key, String requestBody) {
        String payloadHash = DigestUtils.sha256Hex(requestBody);
        String lockKey = "idemp:" + key;
        
        Boolean acquired = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, "PROCESSING:" + payloadHash, Duration.ofMinutes(2));

        if (Boolean.TRUE.equals(acquired)) {
            return new IdempotencyLock(Status.ACQUIRED, null);
        }

        String existingVal = redisTemplate.opsForValue().get(lockKey);
        if (existingVal != null && !existingVal.contains(payloadHash)) {
            throw new IdempotencyMismatchException("Payload altered for idempotency key: " + key);
        }
        if (existingVal != null && existingVal.startsWith("PROCESSING:")) {
            throw new ConcurrentRequestException("Request currently processing. Retry shortly.");
        }
        return new IdempotencyLock(Status.CACHED, existingVal);
    }
}

Answer Key & Deep-Dive Explanation

Part A (Why 2PC Fails in Microservices):
• Blocking Coordinator: 2PC holds database row locks across remote network calls across multiple microservices throughout the prepare/commit phase.
• Latency & Availability Collapse: If one participant or network partition delays response, all databases hold locks, starving connection pools (CAP theorem: sacrificing availability for consistency).
• Heterogeneous Polyglot Backends: Message brokers (Kafka), NoSQL (Mongo, DynamoDB), and third-party SaaS APIs (Stripe) do not support XA/2PC protocols.

Part B (Choreography vs Orchestration):
• Choreography (Event-Driven): Services react to domain events published to Kafka.
Pros: Loose coupling, high throughput, no central bottleneck.
Cons: High cognitive load, difficult end-to-end observability, risk of cyclic event storms, hard to track distributed transaction state.
• Orchestration (Central Coordinator): A dedicated workflow engine explicitly commands participants (reserveStock, chargeCard, compensateInventory).
Pros: Clear state machine visibility, easy timeout handling, no cyclic dependencies.
Cons: Orchestrator can become a single point of failure and bottleneck if overloaded.

Part C (Compensating Transactions & Forward Recovery):
• The Saga executes Compensating Actions in reverse order: refundPayment(), then releaseStockReservation(), and transitions Order to CANCELLED.
• Pivot Transaction: The point of no return. Once Payment succeeds, subsequent steps must either succeed or be retried indefinitely (forward recovery).
• If a compensating step fails (e.g., Payment refund returns 500), it cannot be rolled back via DB ACID. The Saga engine must retry with exponential backoff and publish to a Human-in-the-Loop dead-letter queue.

Answer Key & Deep-Dive Explanation

Part A (ThreadLocal Loss Across Thread Pool Boundaries):
Distributed tracing frameworks (Micrometer Tracing, OpenTelemetry, Logback MDC) store traceId and spanId in Java ThreadLocal variables tied to the incoming HTTP request thread.
When CompletableFuture.supplyAsync() runs without an explicit ContextExecutorService or TaskDecorator, the work executes on a worker thread from ForkJoinPool.commonPool().

Part B (W3C Trace Context Header Specification):
Format: traceparent: {version}-{trace_id}-{parent_id/span_id}-{trace_flags}
Example: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
• 00: Version 1.
• 4bf92f3577b34da6...: 16-byte global Trace ID (constant across entire request call graph).
• 00f067aa0ba902b7: 8-byte Parent Span ID for the current hop.
• 01: Bitmask flags (e.g. 01 = sampled / recorded).
Standardization ensures Java, Go, Node.js, and Python services seamlessly connect telemetry graphs.

The producer must use an OpenTelemetry TextMapPropagator to inject the active trace context into Kafka message RecordHeaders (e.g. key: traceparent).
The Kafka consumer extracts the headers upon receipt, recreates the OpenTelemetry SpanContext, and scopes the consumer thread MDC before dispatching to the listener method.

Answer Key & Deep-Dive Explanation

Part A (Cascading Failure & Thread Pool Starvation):
• Tomcat has a finite incoming request thread pool (default 200 threads).
• When the remote service slows down to 5 seconds per call, 40 incoming requests per second will saturate all 200 worker threads in just 5 seconds (Little's Law: $L = \lambda \times W$).
• Subsequent requests for fast, unrelated endpoints (like /health, /orders/status, /products) are queued or rejected with HTTP 503. The caller service completely collapses.

Part B (Resilience4j State Machine & Sliding Window):
1. CLOSED: All calls pass to the remote service. Calls are recorded in a sliding window (e.g. last 100 calls or last 60 seconds). If failure rate exceeds failureRateThreshold (e.g., 50%) after minimum calls (minimumNumberOfCalls = 20), the circuit transitions to OPEN.
2. OPEN: All incoming calls are short-circuited immediately with CallNotPermittedException without hitting the network, executing fallback logic in microseconds.
3. HALF_OPEN: After waitDurationInOpenState (e.g., 30s), circuit transitions to HALF_OPEN, permitting a limited trial probe of calls (permittedNumberOfCallsInHalfOpenState = 10).
4. If trial failure rate is below threshold, it returns to CLOSED; if failures persist, it transitions back to OPEN.

Part C (Slow Call Rate vs Failure Rate):
A call returning HTTP 200 after 8 seconds is functionally worse than an immediate HTTP 500 error because it ties up threads, DB connections, and sockets.
Resilience4j tracks slowCallDurationThreshold (e.g., 2s). If 50% of calls take longer than 2 seconds, the circuit opens, protecting server threads before total collapse.

Part A (The Dual-Write Failure Scenarios):
1. Ghost Event: kafkaTemplate.send() succeeds and emits the message to Kafka. However, right after, PostgreSQL fails to commit (e.g. database constraint violation, connection timeout, disk full). Result: Downstream inventory services deduct stock for an order that does not exist in the database!

Kafka is not an XA-compliant resource that participates in local database ACID transactions.

• Write the business record (orders) and an event record (outbox_events) within the same atomic local database transaction.
• Approach 1 (Polling Publisher): A background scheduled worker polls SELECT * FROM outbox_events WHERE status = 'PENDING' and sends to Kafka, then marks sent. (Drawback: polling latency, DB CPU load, table lock contention).
• Approach 2 (Log-based CDC with Debezium): Debezium tails PostgreSQL Write-Ahead Log (WAL) directly. Zero application polling overhead, sub-millisecond event streaming to Kafka, guarantees at-least-once delivery.

Answer Key & Deep-Dive Explanation

Part A (RPO vs RTO):
• RPO (Recovery Point Objective): The maximum acceptable data loss measured in time. (RPO = 1s means you cannot lose more than 1 second of committed transactions).
• RTO (Recovery Time Objective): The maximum acceptable downtime before the service is fully restored. (RTO = 5s means failover must restore operational traffic within 5 seconds).

Part B (The CAP Theorem & Split-Brain Hazard):
According to the CAP Theorem, across a wide-area network partition ($P$), a distributed system must choose between Consistency ($C$) and Availability ($A$).
If both regions allow concurrent writes with asynchronous replication:
1. Conflicting writes occur (Last-Write-Wins overwrites data silently).
2. Account balances can be double-spent in two regions simultaneously before replication catches up.
3. When the partition heals, reconciling diverged relational database states requires complex manual reconciliation.

Part C (Architectural Mitigation Strategies):
1. User Pinning (Home Region Partitioning): Users are cryptographically or geographically assigned to a primary home region (e.g. based on Account ID modulo or residence). All write transactions for User X are routed strictly to their home region. In disaster failover, traffic shifts to the standby region only after fencing old writes.
2. CRDTs (Conflict-Free Replicated Data Types): For collaborative or counter-based services (e.g. shopping carts, inventory counters), use State-based or Operation-based CRDTs where operations are mathematically commutative and converge automatically without locks.
