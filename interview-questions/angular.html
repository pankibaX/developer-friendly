Change Detection & Performance Question 1 of 20
📌 1. Concept Covered
ChangeDetectionStrategy.OnPush, strict reference equality checks (===), object/array in-place mutability traps, and immutable state updates.
❓ 2. Question
A developer optimizes an enterprise data grid by adding changeDetection: ChangeDetectionStrategy.OnPush. Look at the component code snippet.

Part A: When the user clicks "Add Item", the item is pushed into the array, but the UI table fails to display the new item. Why does ChangeDetectionStrategy.OnPush ignore in-place array mutations like items.push()?
Part B: What three triggers cause an OnPush component to re-evaluate its template?
Part C: How do you fix this using immutable state spread operators, and what is the difference between ChangeDetectorRef.detectChanges() versus ChangeDetectorRef.markForCheck()?
💻 3. Code Challenge
import { Component, ChangeDetectionStrategy } from '@angular/core'; import { CommonModule } from '@angular/common'; @Component({ selector: 'app-order-list', standalone: true, imports: [CommonModule], changeDetection: ChangeDetectionStrategy.OnPush, template: ` <button (click)="addItem()">Add Item</button> <ul> <li *ngFor="let item of items">{{ item.name }}</li> </ul> ` }) export class OrderListComponent { @Input() items: Item[] = []; addItem() { this.items.push({ id: Date.now(), name: 'New Item' }); } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Part A (Reference Equality & The Mutability Trap):
• Under default change detection, Zone.js checks every component on every asynchronous event by dirty-checking values.
• Under ChangeDetectionStrategy.OnPush, Angular skips the component subtree unless its inputs change by object reference (evaluated via Object.is(oldVal, newVal) / ===).
• this.items.push(...) mutates the existing array in-place: the array memory reference remains identical (oldItems === newItems).
• Angular assumes nothing has changed and skips template re-rendering.

Part B (The 3 Triggers of OnPush Change Detection):
1. An @Input() property reference changes to a new object or primitive.
2. An event originates directly from the component itself or one of its children (e.g. (click), (keyup)).
3. An explicit call is made to ChangeDetectorRef.markForCheck() (or an async pipe / Signal emits a new value).

Part C (Immutable Spread & markForCheck vs detectChanges):
• Fix: Create a new array reference: this.items = [...this.items, newItem];.
• markForCheck(): Marks the component and all its ancestors up to the root as dirty, requesting a pass during the next scheduled change detection cycle.
• detectChanges(): Runs change detection synchronously on the component and its children immediately, which can cause ExpressionChangedAfterItHasBeenCheckedError if abused.

Architectural / Code SolutionTypeScript / HTML
addItem() {
  const newItem = { id: Date.now(), name: 'New Item' };
  this.items = [...this.items, newItem]; // New reference triggers OnPush
}

Removes ChangeDetectionStrategy.OnPush to go back to Default change detection or injects ChangeDetectorRef and calls detectChanges() on every event.
🌟 Advanced / Expert Response
Explains reference equality checking (Object.is), enforces immutable state updates with array spread, and clearly contrasts markForCheck() with detectChanges().
Reactivity Architecture (v16–v18) Question 2 of 20
📌 1. Concept Covered
Fine-grained reactivity with Angular Signals (signal, computed, effect), glitch-free synchronous dependency tracking, and interoperability with RxJS (toSignal, toObservable).
❓ 2. Question
An e-commerce checkout page manages cart items, discount codes, and taxes using Angular 17/18 Signals. Look at the code snippet.

Part A: What is the core architectural difference between Angular Signals (synchronous value containers with dependency tracking) and RxJS Observables (asynchronous push-based streams)?
Part B: Look at the computed() block in the code. Why is calling taxAmount.set(...) inside a computed() strictly forbidden by the Angular compiler, throwing NG0600: Writing to signals is not allowed in a computed?

💻 3. Code Challenge
import { Injectable, signal, computed } from '@angular/core'; @Injectable({ providedIn: 'root' }) export class CartStateService { cartItems = signal<CartItem[]>([]); taxRate = signal<number>(0.08); taxAmount = signal<number>(0); subtotal = computed(() => { return this.cartItems().reduce((acc, item) => acc + item.price, 0); }); total = computed(() => { const calcTax = this.subtotal() * this.taxRate(); this.taxAmount.set(calcTax); return this.subtotal() + calcTax; }); }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Part A (Signals vs Observables Comparison):
• Signals: Synchronous state primitives with pull-based evaluation and dynamic dependency tracking. They always have a current value, execute glitch-free (eliminating diamond dependency problems), and enable fine-grained DOM updates without Zone.js.
• RxJS Observables: Push-based asynchronous streams over time. Required for complex event coordination (debouncing, race conditions, cancellation via switchMap, retry logic, WebSockets).

Part B (Computed Signal Purity & NG0600):
• computed() signals are strictly designed to be pure derivation functions.
• Writing to another signal inside a computed derivation introduces side effects, which can cause cyclic dependency loops and unpredictable rendering order.
• taxAmount should simply be another derived computed() signal, not a writable signal updated as a side effect.

Part C (When to Use What):
• Use Signals for: Synchronous UI component state, derived values, inputs, queries, and replacing Zone.js for change detection.
• Use RxJS for: HTTP calls, debounced search inputs, WebSocket real-time feeds, interval polling, and complex asynchronous stream composition.

🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Part A (Closure Scope Retaining Component Instances):
• metricsService is a singleton service that lives for the entire application lifetime.
• When subscribe() is called in DashboardMetricsComponent, the callback closure captures this (the component instance).
• When the user navigates away, the component view is removed from the DOM, but the singleton service retains a direct reference to the component instance in its observer list.
• The Garbage Collector cannot free the component, leading to massive memory leaks, duplicate callbacks, and stale event executions.

Part B (takeUntilDestroyed via DestroyRef):
• takeUntilDestroyed automatically hooks into Angular's DestroyRef.
• When the component or injector is destroyed, the operator automatically emits a completion signal and unregisters the subscription, releasing memory.

Part C (Injection Context Requirement):
• If called in the constructor(), takeUntilDestroyed() automatically infers the DestroyRef from the active injection context.
• If called in ngOnInit(), the constructor injection context has ended. You must explicitly inject DestroyRef and pass it: takeUntilDestroyed(this.destroyRef).

🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Part A (The Element Injector Shadowing Trap):
• ShoppingCartService is configured with providedIn: 'root', creating a single global singleton instance in the Root Injector.
• However, CheckoutModalComponent specifies providers: [ShoppingCartService] on its @Component decorator.
• This instructs Angular's Element Injector to instantiate a brand-new, isolated instance of ShoppingCartService scoped strictly to this modal component and its children.
• The modal injects the newly created empty service, shadowing the root singleton. Any modifications inside the modal affect only the shadow instance!

1. Platform Injector: Singleton across multiple Angular applications on the same page (e.g. DomSanitizer).
2. Root Injector: Application-level singletons (providedIn: 'root').
3. Environment Injector: Created by routed components or createEnvironmentInjector().
4. Element Injector: Created at each DOM component/directive level. Traversed upwards until a provider is found.

Part C (When Component-Level Providers are Desirable):
Component-level providers are desired when state must be tied strictly to a component's lifecycle:
• Reusable form controls or complex wizard steps that require clean, isolated state per widget instance.
• Destroying the component automatically garbage-collects the service instance.

import { HttpInterceptorFn } from '@angular/common/http'; import { inject } from '@angular/core'; export const authInterceptor: HttpInterceptorFn = (req, next) => { const authService = inject(AuthService); const token = authService.getToken(); const cloned = req.clone({ setHeaders: { Authorization: `Bearer ${token}` } }); return next(cloned).pipe( catchError((error: HttpErrorResponse) => { if (error.status === 401) { return authService.refreshToken().pipe( switchMap(newToken => { return next(req.clone({ setHeaders: { Authorization: `Bearer ${newToken}` } })); }) ); } return throwError(() => error); }) ); };
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Part A (HttpRequest Immutability):
• HTTP requests are immutable because interceptors form a bidirectional pipeline.
• If an interceptor or retry mechanism needs to resend a request, it requires the pristine original request.
• Mutating the request object in-place would corrupt downstream retries, caching proxies, and cause race conditions across concurrent interceptor chains.

Part B (Preventing the 401 Infinite Loop):
• If authService.refreshToken() invokes the backend /api/auth/refresh endpoint, that request also passes through this interceptor!
• If the refresh token has expired, /api/auth/refresh returns 401, triggering another refresh call infinitely until the call stack or network crashes.
• Fix: Check req.url.includes('/auth/refresh'). If the failing request is the refresh endpoint itself, bypass refresh logic, log out the user, and redirect to login.

Part C (Functional Interceptors & inject()):
• HttpInterceptorFn runs inside an Angular injection context.
• You call inject(ServiceName) directly at the function level without needing class constructors or HTTP_INTERCEPTORS multi-provider tokens.

Architectural / Code SolutionTypeScript / HTML
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const auth = inject(AuthService);
  const router = inject(Router);

  // Exclude refresh endpoint from interceptor retry logic
  if (req.url.includes('/api/auth/refresh')) {
    return next(req);
  }

  const authReq = req.clone({ setHeaders: { Authorization: `Bearer ${auth.token()}` } });

  return next(authReq).pipe(
    catchError((err: HttpErrorResponse) => {
      if (err.status === 401) {
        return auth.refreshToken().pipe(
          switchMap(t => next(req.clone({ setHeaders: { Authorization: `Bearer ${t}` } }))),
          catchError(refreshErr => {
            auth.logout();
            router.navigate(['/login']);
            return throwError(() => refreshErr);
          })
        );
      }
      return throwError(() => err);
    })
  );
};

🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Part A (Debouncing Async Validators with timer):
• By default, asyncValidators execute on every single keystroke event.
• Typing rapidly fires multiple pending asynchronous HTTP requests. If network responses arrive out of order, stale responses can overwrite fresh validation states!
• Fix: Wrap the check in timer(300) followed by switchMap(). If the user types another character within 300ms, the timer is cancelled and prior pending HTTP requests are aborted.

Part B (updateOn: 'change' vs 'blur'):
• updateOn: 'change' (default): Emits values and runs validators on every character typed.
• updateOn: 'blur': Runs validation only when the user tabs or clicks away from the input field. For heavy async database validations, setting updateOn: 'blur' slashes server validation requests by 90%.

Part C (Typed Reactive Forms Benefits):
• Since Angular 14, FormGroup and FormControl are strictly typed.
• form.controls.nonExistentField triggers a compile-time TypeScript error (Property does not exist on type...).
• form.value produces a strongly typed interface (e.g. { username: string | null }), eliminating runtime undefined bugs.

Architectural / Code SolutionTypeScript / HTML
export function debouncedUsernameValidator(userService: UserService): AsyncValidatorFn {
  return (control: AbstractControl): Observable<ValidationErrors | null> => {
    if (!control.value) return of(null);
    return timer(300).pipe(
      switchMap(() => userService.checkUsername(control.value)),
      map(taken => taken ? { usernameTaken: true } : null),
      catchError(() => of(null))
    );
  };
}

Answer Key & Deep-Dive Explanation

Part A (The Multiple Angular Runtime Collision):
• Angular relies on global singletons stored in its runtime: the PlatformRef, the Root Injector, and Zone.js.
• If @angular/core is not shared as a singleton, the Shell bundles its own copy of Angular, and the remote app bundles a second copy of Angular.
• When the remote loads, it attempts to initialize a second PlatformRef in the same browser window, triggering fatal runtime crashes (Cannot create platform when another platform exists).

Part B (singleton vs strictVersion in Module Federation):
• singleton: true: Guarantees that only one instance of the library is loaded in memory and shared across all micro-frontends.
• strictVersion: true: If host and remote have mismatched semver versions (e.g. 17.1 vs 17.3), Webpack refuses to share and fails with an error.
• If strictVersion: false (recommended for minor version variance), Webpack picks the highest compatible version.

• customElements.define('payment-widget', element) registers it with the browser.

• Heavy synchronous computations in change detection, large loops, or un-debounced inputs block the browser's single JavaScript main thread.
• If the main thread is blocked for > 200ms, user clicks lag, resulting in an unacceptable INP score.
