Spring Core & AOP Mechanics Question 1 of 10
📌 1. Concept Covered
Spring AOP dynamic proxy mechanics (CGLIB/JDK Dynamic Proxies) and why internal self-invocation (this.method()) completely bypasses proxy interceptors for @Transactional, @Async, and @Cacheable.
❓ 2. Question
Look at the OrderProcessingService in the code snippet.

Part A: When a client calls submitOrder(order), which in turn calls executePayment(order), why does executePayment() fail to start a new transaction?
Part B: If paymentClient.charge() throws an unexpected RuntimeException, why does the database insert performed in submitOrder() still commit instead of rolling back?
Part C: What are the clean architectural fixes to solve this? (Compare self-injection vs service decomposition).
💻 3. Code Challenge
@Service public class OrderProcessingService { @Autowired private OrderRepository orderRepository; @Autowired private PaymentClient paymentClient; public void submitOrder(Order order) { order.setStatus(OrderStatus.PENDING); orderRepository.save(order); executePayment(order); } @Transactional(propagation = Propagation.REQUIRES_NEW) public void executePayment(Order order) { paymentClient.charge(order.getCustomerId(), order.getAmount()); order.setStatus(OrderStatus.CONFIRMED); orderRepository.save(order); } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Root Cause: Spring's declarative transaction management operates via proxies (CGLIB subclassing or JDK dynamic interfaces). When an external client calls a bean method, it invokes the proxy object, which runs the transaction interceptor before delegating to the target object.

However, when submitOrder() calls executePayment() internally, it uses the direct Java this reference. this points to the raw unproxied instance, completely bypassing the Spring AOP interceptor stack! As a result, @Transactional(propagation = Propagation.REQUIRES_NEW) is totally ignored; execution runs in standard auto-commit mode without transaction boundaries.

Recommended Clean Architectural FixJava
// Decompose into distinct cohesive domain services
@Service
public class OrderProcessingService {
    private final OrderRepository orderRepository;
    private final OrderPaymentService orderPaymentService;

    public OrderProcessingService(OrderRepository orderRepository, OrderPaymentService orderPaymentService) {
        this.orderRepository = orderRepository;
        this.orderPaymentService = orderPaymentService;
    }

    @Transactional
    public void submitOrder(Order order) {
        order.setStatus(OrderStatus.PENDING);
        orderRepository.save(order);
        orderPaymentService.executePayment(order);
    }
}

@Service
public class OrderPaymentService {
    private final PaymentClient paymentClient;
    private final OrderRepository orderRepository;

    public OrderPaymentService(PaymentClient paymentClient, OrderRepository orderRepository) {
        this.paymentClient = paymentClient;
        this.orderRepository = orderRepository;
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void executePayment(Order order) {
        paymentClient.charge(order.getCustomerId(), order.getAmount());
        order.setStatus(OrderStatus.CONFIRMED);
        orderRepository.save(order);
    }
}

Suggests using ((OrderProcessingService) AopContext.currentProxy()).executePayment(order) or @Autowired private OrderProcessingService self without recognizing that this is an anti-pattern showing poor component design.
🌟 Advanced / Expert Response
Articulates Spring AOP proxy interception mechanics immediately, explains why AspectJ compile-time/load-time weaving differs from Spring runtime proxies, and advocates separating payment into a dedicated service.

🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

        super(message, cause);

Transaction Propagation & Boundaries Question 3 of 10
📌 1. Concept Covered
Transaction boundary propagation (REQUIRED vs REQUIRES_NEW) and the TransactionStatus.setRollbackOnly() marker causing UnexpectedRollbackException when exceptions are swallowed in try-catch.
❓ 2. Question
Look at InvoiceService and NotificationService in the code snippet. In generateInvoice(), the call to notificationService.sendNotification() is wrapped in a try-catch block that logs and swallows the exception.

When run with an invalid email, the method throws:
org.springframework.transaction.UnexpectedRollbackException: Transaction silently rolled back because it has been marked as rollback-only.

Why did the outer transaction roll back even though the exception was caught, and how do you ensure the invoice is saved even if the notification fails?
💻 3. Code Challenge
@Service public class InvoiceService { @Autowired private InvoiceRepository invoiceRepository; @Autowired private NotificationService notificationService; @Transactional public void generateInvoice(InvoiceRequest request) { Invoice invoice = new Invoice(request); invoiceRepository.save(invoice); try { notificationService.sendNotification(invoice); } catch (Exception ex) { log.error("Failed to notify customer", ex); } } } @Service public class NotificationService { @Transactional public void sendNotification(Invoice invoice) { if (invoice.getEmail() == null) { throw new IllegalArgumentException("Customer email required"); } } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

The Root Cause: Both methods use the default propagation Propagation.REQUIRED. When sendNotification() is called, it does NOT start a new transaction; it joins the existing physical transaction started by generateInvoice().

When sendNotification() throws IllegalArgumentException (an unchecked exception), its Spring transaction interceptor catches it and marks the shared physical transaction as rollback-only (TransactionStatus.setRollbackOnly()).

Even though InvoiceService catches and swallows the exception in its Java try-catch, when generateInvoice() finishes, the Spring transaction manager attempts to commit the physical transaction. It detects that the transaction was marked rollback-only by an inner method, aborts the commit, rolls back everything, and throws UnexpectedRollbackException!

Fix OptionsJava
// Solution 1: Isolate in an independent physical transaction
@Service
public class NotificationService {

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void sendNotification(Invoice invoice) {
        // Runs in its own separate transaction; failure marks only its own transaction for rollback
    }
}

// Solution 2: Preferred Enterprise Design - Decouple via Spring Application Events or MQ
@Transactional
public void generateInvoice(InvoiceRequest request) {
    Invoice invoice = new Invoice(request);
    invoiceRepository.save(invoice);
    eventPublisher.publishEvent(new InvoiceGeneratedEvent(invoice.getId()));
}
⚠️ Junior / Beginner Response
Thinks the `try-catch` was in the wrong place or that Spring is "broken" because it ignored standard Java catch logic.
🌟 Advanced / Expert Response
Immediately explains the shared physical transaction boundary, the `setRollbackOnly()` marker, and architectural options (`REQUIRES_NEW`, `@Async`, or event-driven messaging).
Dependency Injection & Lifecycle Question 4 of 10
📌 1. Concept Covered
Spring bean lifecycle instantiation phases, constructor vs setter injection, and why Spring Boot 2.6+ / 3.x disabled circular references by default (BeanCurrentlyInCreationException).
❓ 2. Question
Look at UserService and AuditService in the code snippet. When the Spring Boot application boots up, it crashes with:
The dependencies of some of the beans in the application context form a cycle: UserService -> AuditService -> UserService.

Part A: Why does constructor injection fail with circular references while field/setter injection used to allow it in older Spring versions?
Part B: Why did Spring Boot disable circular references by default starting in Spring Boot 2.6?
Part C: How do you resolve this properly without resorting to lazy hacks?
💻 3. Code Challenge
@Service public class UserService { private final AuditService auditService; private final UserRepository userRepository; public UserService(AuditService auditService, UserRepository userRepository) { this.auditService = auditService; this.userRepository = userRepository; } public void register(User user) { userRepository.save(user); auditService.logAction("USER_REGISTERED", user.getId()); } public User getUser(Long id) { return userRepository.findById(id).orElse(null); } } @Service public class AuditService { private final UserService userService; private final AuditLogRepository auditLogRepository; public AuditService(UserService userService, AuditLogRepository auditLogRepository) { this.userService = userService; this.auditLogRepository = auditLogRepository; } public void logAction(String action, Long userId) { User user = userService.getUser(userId); auditLogRepository.save(new AuditEntry(action, user)); } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Why Constructor Injection Crashes: With constructor injection, Spring must instantiate bean A by calling its constructor. To call bean A's constructor, bean B must already exist. But to instantiate bean B, bean A must already exist. It is a fundamental chicken-and-egg deadlock at the JVM bytecode level before any object instance can be created in heap.

In contrast, field/setter injection allowed Spring to use its 3-level singleton cache (early bean references): it instantiated an uninitialized bean A, exposed its raw reference to the cache, injected bean A into bean B, and then finished injecting bean B into bean A.

Why Spring Boot Disabled It: Circular dependencies violate the Single Responsibility Principle and create hard coupling that leads to hidden initialization order bugs, memory leaks, and proxy generation failures (e.g., when @Async or transactional proxies wrap one of the cyclic beans).

Architectural Resolution: Decouple via EventsJava
// 1. UserService publishes an event instead of calling AuditService directly
@Service
public class UserService {
    private final UserRepository userRepository;
    private final ApplicationEventPublisher eventPublisher;

    public UserService(UserRepository userRepository, ApplicationEventPublisher eventPublisher) {
        this.userRepository = userRepository;
        this.eventPublisher = eventPublisher;
    }

    public void register(User user) {
        userRepository.save(user);
        eventPublisher.publishEvent(new UserRegisteredEvent(user));
    }
}

// 2. AuditService listens to events; no dependency on UserService!
@Component
public class AuditService {
    private final AuditLogRepository auditLogRepository;

    public AuditService(AuditLogRepository auditLogRepository) {
        this.auditLogRepository = auditLogRepository;
    }

    @EventListener
    public void onUserRegistered(UserRegisteredEvent event) {
        auditLogRepository.save(new AuditEntry("USER_REGISTERED", event.getUser()));
    }
}
⚠️ Junior / Beginner Response
Recommends adding @Lazy to the constructor or setting spring.main.allow-circular-references=true in application.properties.
🌟 Advanced / Expert Response
Rejects `@Lazy` as a band-aid hiding architectural rot; redesigns dependencies using Spring Application Events or extracts a third intermediary service.

💻 3. Code Challenge
@Component @Scope(ConfigurableBeanFactory.SCOPE_PROTOTYPE) public class ReportContext { private String tenantId; private List<String> buffer = new ArrayList<>(); public void init(String tenantId) { this.tenantId = tenantId; } public void addData(String row) { buffer.add(row); } public List<String> getBuffer() { return buffer; } } @Service public class ReportJobRunner { @Autowired private ReportContext reportContext; public void runJob(String tenantId, List<String> records) { reportContext.init(tenantId); records.forEach(reportContext::addData); persistReport(reportContext); } private void persistReport(ReportContext ctx) { } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Root Cause: ReportJobRunner is a singleton bean instantiated once during Spring application startup. Its dependencies are resolved and injected only once at startup. Therefore, only one single instance of ReportContext is created and bound to ReportJobRunner forever!

When multiple concurrent worker threads call runJob(), they all mutate the exact same reportContext instance and its unsynchronized ArrayList buffer, causing disastrous cross-tenant data leaks and race conditions.

        ReportContext freshContext = reportContextProvider.getObject(); // Returns a new prototype instance every time
        freshContext.init(tenantId);
        records.forEach(freshContext::addData);
        persistReport(freshContext);
    }
}

Spring Security & Concurrency Question 7 of 10
📌 1. Concept Covered
SecurityContextHolder storage strategies (ThreadLocal) and the security context loss problem when spawning background threads with @Async or CompletableFuture.
❓ 2. Question
Look at UserReportService.generateUserReport() in the code snippet. A logged-in user triggers an asynchronous report export. However, inside the @Async method, SecurityContextHolder.getContext().getAuthentication() returns null, causing an unhandled NullPointerException.

Part A: Why is the authentication token missing in the @Async worker thread?
Part B: Why is configuring SecurityContextHolder.setStrategyName(SecurityContextHolder.MODE_INHERITABLETHREADLOCAL) dangerous in thread-pool environments (such as Tomcat or ThreadPoolTaskExecutor)?
Part C: What is the production-grade way to propagate security context to thread pools in Spring Boot?
💻 3. Code Challenge
@Service public class UserReportService { @Async public CompletableFuture<ReportResult> generateUserReport() { Authentication auth = SecurityContextHolder.getContext().getAuthentication(); String currentUsername = auth.getName(); ReportResult result = buildReportForUser(currentUsername); return CompletableFuture.completedFuture(result); } private ReportResult buildReportForUser(String username) { return new ReportResult(username, System.currentTimeMillis()); } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Why Authentication is Null: By default, Spring Security uses SecurityContextHolder.MODE_THREADLOCAL. The authenticated context lives strictly on the HTTP request thread. When @Async runs, it executes on a separate worker thread from the task executor pool, which starts with an empty ThreadLocal map.

Why `MODE_INHERITABLETHREADLOCAL` is Dangerous: InheritableThreadLocal only copies context when a new thread is spawned. Thread pools pre-allocate worker threads! A pooled worker thread will retain stale credentials from a previous user and execute subsequent requests under the wrong identity (severe authorization bypass and tenant data leak).

Production-Grade Solution: TaskDecoratorJava
@Configuration
@EnableAsync
public class AsyncSecurityConfig {

    @Bean("taskExecutor")
    public Executor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(10);
        executor.setMaxPoolSize(50);
        executor.setQueueCapacity(100);
        executor.setThreadNamePrefix("async-exec-");
        
        // Explicitly copies security context when task is submitted, and clears it when task finishes!
        executor.setTaskDecorator(runnable -> {
            SecurityContext context = SecurityContextHolder.getContext();
            return () -> {
                try {
                    SecurityContextHolder.setContext(context);
                    runnable.run();
                } finally {
                    SecurityContextHolder.clearContext(); // Prevents thread-pool contamination!
                }
            };
        });
        
        executor.initialize();
        return executor;
    }
}
⚠️ Junior / Beginner Response
Recommends passing username as a parameter or setting `MODE_INHERITABLETHREADLOCAL` without recognizing thread reuse contamination.
🌟 Advanced / Expert Response
Details ThreadLocal pool reuse hazards, configures a `TaskDecorator` with `DelegatingSecurityContextRunnable` or `DelegatingSecurityContextAsyncTaskExecutor`, and ensures `clearContext()` is called in `finally`.

❓ 2. Question

@RestController @RequestMapping("/api/orders") public class OrderMetricsController { private final MeterRegistry meterRegistry; public OrderMetricsController(MeterRegistry meterRegistry) { this.meterRegistry = meterRegistry; } @PostMapping("/submit") public ResponseEntity<String> submitOrder( @RequestHeader("X-Request-Id") String requestId, @RequestBody OrderDto dto) { meterRegistry.counter("orders.received", "requestId", requestId).increment(); return ResponseEntity.ok("Submitted"); } }

Not Rated
Answer Key & Deep-Dive Explanation

• /actuator/heapdump: Allows any external attacker to download the complete JVM heap snapshot (recovering plain-text passwords, customer PII, credit card numbers).
• /actuator/shutdown: Allows malicious actors to terminate the service remotely.

📌 1. Concept Covered

❓ 2. Question
Look at OrderService and OrderEmailNotifier in the code snippet. When an order is created, OrderService saves it and publishes an OrderCreatedEvent. In OrderEmailNotifier, the listener runs in TransactionPhase.AFTER_COMMIT, sends an email, and updates order.setEmailSent(true).

The email is sent successfully, but order.setEmailSent(true) is NEVER saved in the database! Yet, no exception is logged.

Why does database persistence fail silently in AFTER_COMMIT, and what is the proper architectural pattern?
💻 3. Code Challenge
@Service public class OrderService { @Autowired private OrderRepository orderRepository; @Autowired private ApplicationEventPublisher eventPublisher; @Transactional public void createOrder(Order order) { orderRepository.save(order); eventPublisher.publishEvent(new OrderCreatedEvent(order.getId())); } } @Component public class OrderEmailNotifier { @Autowired private OrderRepository orderRepository; @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT) public void onOrderCreated(OrderCreatedEvent event) { Order order = orderRepository.findById(event.getOrderId()).orElseThrow(); sendConfirmationEmail(order); order.setEmailSent(true); orderRepository.save(order); } private void sendConfirmationEmail(Order order) { } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

The Root Cause: In AFTER_COMMIT, the physical database transaction has already completed and committed. The underlying JDBC connection was either closed or unbound from the current thread.

When the listener calls orderRepository.save(order), Spring Data JPA / Hibernate sees that the current thread's transaction synchronization is still active but in a committed, read-only completion state. Hibernate's persistence context is not flushed to the database, and no subsequent commit is ever issued. The dirty entity changes are simply discarded when the thread terminates, without throwing an error!

Idiomatic Architectural FixesJava
// Solution 1: Explicitly open a fresh independent transaction
@Component
public class OrderEmailNotifier {
    private final OrderRepository orderRepository;

    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void onOrderCreated(OrderCreatedEvent event) {
        Order order = orderRepository.findById(event.getOrderId()).orElseThrow();
        sendConfirmationEmail(order);
        order.setEmailSent(true);
        orderRepository.save(order);
    }
}

// Solution 2: Asynchronous Outbox / Event Listener (Recommended)
@Component
public class OrderEmailNotifier {
    @Async
    @TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
    @Transactional
    public void onOrderCreated(OrderCreatedEvent event) {
        // Runs in separate worker thread, opens fresh transaction, doesn't block caller
    }
}

Answer Key & Deep-Dive Explanation

Part A (Spring Graceful Shutdown Behavior): When Spring Boot receives SIGTERM with server.shutdown=graceful:
1. Embedded Tomcat stops accepting new incoming TCP connections immediately.
2. It permits active in-flight HTTP requests a grace period (timeout-per-shutdown-phase: 30s) to complete processing.

Part B (The Kubernetes Race Condition): When Kubernetes terminates a pod during a deployment:
• Event 1: Kubernetes sends SIGTERM to the container.
• Event 2: Kubernetes API server deregisters the pod IP from the Service Endpoints slice and propagates IP table updates across all cluster nodes (kube-proxy / Ingress controller).
The Trap: These two events happen asynchronously in parallel! Because propagating IP table updates across all nodes takes 1 to 3 seconds, the ingress controller continues routing new user requests to the pod AFTER the pod has already received SIGTERM and stopped accepting new connections. Result: HTTP 502 / Connection Refused!

Part C (The Solution: preStop Hook): Introduce a container preStop: exec: command: ["/bin/sleep", "15"]. When Kubernetes initiates shutdown, the pod sleeps for 15 seconds before Spring Boot receives SIGTERM. During these 15 seconds, Kubernetes removes the pod IP from all routers while the Spring container continues serving active and newly arriving traffic smoothly!

Zero-Downtime Kubernetes Pod Specyaml
spec:
  containers:
    - name: app
      image: order-service:latest
      lifecycle:
        preStop:
          exec:
            # Allows ingress controller and kube-proxy 15s to remove IP before Spring receives SIGTERM!
            command: ["/bin/sleep", "15"]
      readinessProbe:
        httpGet:
          path: /actuator/health/readiness
          port: 8080
      terminationGracePeriodSeconds: 45 # Must be larger than preStop (15s) + Spring timeout (30s)
