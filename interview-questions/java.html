Answer Key & Deep-Dive Explanation

Answer to Part A: Prints Set size: 5 (NOT 3). Default Object.hashCode() uses memory address, and Object.equals() checks reference equality (==).

Answer to Part B: Override both equals() and hashCode() using the business identity attributes (id and name). Both methods must be kept consistent with each other so equal objects compute identical hash buckets (see code fix below).

Answer to Part C (Deep Probe):

Correct FixJava

public boolean equals(Object o) {

    if (o == null || getClass() != o.getClass()) return false;

    return id == employee.id && Objects.equals(name, employee.name);
}

@Override
public int hashCode() {
    return Objects.hash(id, name);

💻 3. Code Challenge
public class PaginationService { public List<Transaction> getPaginatedTransactions(List<Transaction> allTransactions, int pageNumber, int pageSize) { return allTransactions.stream() .limit(pageSize) .skip(pageNumber * pageSize) .toList(); } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Root Cause: The developer ordered .limit() BEFORE .skip()!
• Suppose pageSize = 10 and pageNumber = 1 (second page).
• .limit(10) first truncates the entire stream to only the first 10 items.
• Then .skip(10) discards those 10 items. Result: empty list!
• Rule: You must always skip first (advance the offset), and then limit (take the page window).

Fix: skip() then limit()Java
public List<Transaction> getPaginatedTransactions(List<Transaction> allTransactions, int pageNumber, int pageSize) {
    if (allTransactions == null || pageNumber < 0 || pageSize <= 0) {
        return List.of();
    }

    return allTransactions.stream()
        .skip((long) pageNumber * pageSize) // 1. Skip prior pages first!
        .limit(pageSize)                   // 2. Take only current page size!
        .toList();
}

"Streams don't support pagination, use a SQL query" without spotting the reversed method order.
🌟 Advanced / Expert Response

JDK Internals & Sorting Algorithms Question 15 of 20
📌 1. Concept Covered
The sorting algorithms used inside the JDK: Dual-Pivot Quicksort (primitives) vs TimSort (objects), stability requirements, and the Comparison method violates its general contract! crash.
❓ 2. Question
Part A: What sorting algorithms does the JDK use for Arrays.sort(int[]) vs Collections.sort(List<T>)? Why is there no single "best" sorting algorithm?

Part B: In production, the sorting method in the code snippet intermittently crashes with java.lang.IllegalArgumentException: Comparison method violates its general contract! on large datasets. What causes this crash and how do you write a compliant comparator?
💻 3. Code Challenge
public class ProductCatalogSorter { public void sortProducts(List<Product> products) { Collections.sort(products, new Comparator<Product>() { @Override public int compare(Product p1, Product p2) { return (p1.getScore() > p2.getScore()) ? 1 : -1; } }); } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

JDK Sorting Algorithms:
• Primitives (int[], double[]): Uses Dual-Pivot Quicksort (by Vladimir Yaroslavskiy). Average \(O(N \log N)\), in-place, non-stable, highly cache-efficient. Stability is irrelevant for primitives because identical numbers have no distinguishable identity.
• Objects (List<T>, Object[]): Uses TimSort (hybrid of Merge Sort and Insertion Sort). Worst-case \(O(N \log N)\), best-case \(O(N)\) on partially ordered data, and stable (preserves original order of equal items).

Root Cause of the Crash: When p1.getScore() == p2.getScore(), the custom comparator returns -1 instead of 0! This violates:
1. Reflexivity: compare(a, a) must equal 0 (here it returns -1).
2. Symmetry: compare(a, b) == -compare(b, a) (here both return -1).
TimSort uses these mathematical invariants to verify merge boundaries; violating them throws IllegalArgumentException!

Fix: Use Comparator.comparingDouble()Java
public void sortProducts(List<Product> products) {
    products.sort(Comparator.comparingDouble(Product::getScore));

Answer Key & Deep-Dive Explanation

Java 7 vs Java 8 HashMap Internal Evolution:
• Java 7 (Singly Linked List only): When keys collide, they are stored as a linked list in that bucket. If all 10,000 keys hash to bucket 42, the bucket becomes a 10,000-node linked list! Searching requires traversing all nodes, degrading lookup from \(O(1)\) to \(O(N)\). Attackers exploited this via HashDoS attacks (sending crafted HTTP requests with colliding hashes to consume 100% CPU).

• Java 8+ (Treeification to Red-Black Tree):
1. Treeification Threshold: When the number of elements in a single bucket reaches TREEIFY_THRESHOLD = 8 AND the total table capacity is at least MIN_TREEIFY_CAPACITY = 64, the linked list converts into a balanced Red-Black Tree (TreeNode)!
2. Search Complexity: Lookup time drops from \(O(N)\) down to \(O(\log N)\). For 10,000 colliding items, search takes at most ~14 comparisons instead of 10,000!
3. Untreeify Threshold: When elements are removed and the bucket size shrinks to UNTREEIFY_THRESHOLD = 6, the tree is converted back into a standard linked list to save memory overhead.
4. Why Comparable: TreeNode uses Comparable.compareTo() (as implemented in CollidingKey) to balance and order nodes in the Red-Black tree; if keys do not implement Comparable, Java uses System.identityHashCode() as a tiebreaker.

Answer Key & Deep-Dive Explanation

Part A (CommonPool Thread Starvation):
CompletableFuture.supplyAsync(Supplier) without an explicit Executor executes on the shared ForkJoinPool.commonPool(). This pool is sized strictly for CPU-intensive tasks (typically Runtime.getRuntime().availableProcessors() - 1 worker threads).
When blocking HTTP I/O is dispatched to commonPool(), those few worker threads are parked waiting for network responses. Consequently, all other application features utilizing the common pool (parallel streams, other CompletableFutures) starve completely, causing whole-service cascading degradation!

Part B (whenComplete Bug):
whenComplete(BiConsumer) is purely an observer/callback with a void return! Reassigning the local variable result = new OrderSummary(...) has zero effect on the returned stage. If an exception occurred upstream, the returned CompletableFuture remains completed exceptionally with CompletionException, crashing caller code that awaits it.
To transform an exception into a fallback value, one must use .handle((result, ex) -> ...) or .exceptionally(ex -> ...) which return a new stage.

🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Part A (AtomicLong Contention Bottleneck):
AtomicLong stores a single 64-bit volatile long value. Every update executes a tight hardware CAS loop (Compare-And-Swap) targeting that single memory address. When 128 threads hammer the same variable simultaneously:
1. Exactly one thread succeeds on each CPU cycle; the other 127 fail, spin in a loop, and retry.
2. This causes massive CPU L1/L2 cache line bouncing (MESI cache coherency protocol invalidating cache lines across all CPU cores on every write), burning 95%+ CPU on futile retries.

Part B (LongAdder & Striped64 Architecture):
Java 8 introduced LongAdder which extends Striped64:
• Instead of a single volatile counter, it dynamically maintains an array of Cell objects (padded with @Contended to avoid false sharing on cache lines).
• Each thread hashes to a different Cell based on its thread hash (ThreadLocalRandom.getProbe()), modifying its own cell independently with virtually zero thread contention.
• LongAdder.sum() simply aggregates all cells when the value is read. For write-heavy telemetry/counters, LongAdder is 10x-50x faster than AtomicLong.

Part C (The ABA Problem & AtomicStampedReference):
In lock-free data structures (like a Treiber stack), Thread 1 reads value A at memory address \(X\). Thread 1 gets preempted.
Thread 2 changes \(X\) from A to B, and then changes it back from B to A.
When Thread 1 resumes, its CAS checks if \(X == A\). It sees A and assumes nothing changed, proceeding with the swap. However, internal state (or linked nodes) was mutated, leading to silent memory corruption!
Resolution: AtomicStampedReference<V> binds an integer version stamp (or timestamp) to the reference. The CAS only succeeds if both reference == expectedReference AND stamp == expectedStamp.

    }
