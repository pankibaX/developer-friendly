Producer Internals & Reliability Question 1 of 20
📌 1. Concept Covered
Kafka Producer Reliability Guarantees: The interplay between acks=all, topic min.insync.replicas, replication.factor, and enable.idempotence=true to prevent silent data loss during leader broker failovers.
❓ 2. Question
A financial trading team configured their Kafka producer with acks=all. During a planned broker restart, several trading orders sent by the producer were permanently lost, despite the producer receiving successful RecordMetadata acknowledgments!

Part A: Why did setting acks=all fail to prevent data loss if the broker's min.insync.replicas was set to 1?
Part B: What is the difference between setting acks=1 vs acks=all (-1)?
Part C (Deep Probe): What happens when enable.idempotence=true is enabled on the producer, and what headers/sequence numbers are attached to batches?
💻 3. Code Challenge
public class TradeProducerConfig { public static Producer<String, String> createProducer() { Properties props = new Properties(); props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "broker1:9092,broker2:9092,broker3:9092"); props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName()); props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName()); props.put(ProducerConfig.ACKS_CONFIG, "all"); props.put(ProducerConfig.RETRIES_CONFIG, 3); // Topic created with: replication-factor 3, min.insync.replicas 1 return new KafkaProducer<>(props); } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Answer to Part A: acks=all guarantees that the leader waits for all currently active in-sync replicas to acknowledge the write. If 2 follower brokers temporarily fall out of the ISR (In-Sync Replicas list) and min.insync.replicas=1, the leader is the ONLY replica in the ISR! The leader writes locally, acknowledges success to the producer immediately, and if that broker crashes before followers catch up, the message is permanently lost.

Answer to Part B: acks=1 acknowledges as soon as the partition leader writes to its local log without waiting for any followers. acks=all requires the leader plus all current in-sync replicas (satisfying $\ge \text{min.insync.replicas}$) to acknowledge before returning success.

Answer to Part C (Deep Probe): enable.idempotence=true assigns a unique Producer ID (PID) and monotonically increasing sequence numbers per partition. The broker rejects duplicate sequence numbers and maintains exact message ordering even if network timeouts cause producer retries.

Correct FixJava / Broker Config
// 1. Topic Configuration:
// kafka-topics.sh --alter --topic trades --config min.insync.replicas=2

// 2. Producer Configuration:
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "broker1:9092,broker2:9092,broker3:9092");
props.put(ProducerConfig.ACKS_CONFIG, "all");
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true"); // Mandates acks=all, retries=MAX
props.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5); // Safe with idempotence!
⚠️ Junior / Unacceptable Response
  • Believes acks=all means all brokers in the cluster or all replicas must acknowledge.
  • Does not know what min.insync.replicas does.
🌟 Architect-Level Response
  • Articulates that acks=all evaluates against the dynamic In-Sync Replicas (ISR) set, not total replicas.
  • Mandates pairing replication.factor=3 with min.insync.replicas=2 to tolerate 1 broker failure without losing durability.
  • Explains PID and sequence numbers in idempotent producer semantics.

An audit logging system requires that all events for a given userId must be processed in the exact order they occurred. In production, user events occasionally arrive out-of-order at the consumer (e.g. `USER_DELETED` is processed before `USER_CREATED`).

Part A: How does Kafka guarantee message ordering across partitions vs within a single partition?
Part B: In the producer code snippet, why did enabling retries with max.in.flight.requests.per.connection = 5 cause out-of-order delivery?

💻 3. Code Challenge
public class UserAuditProducer { public static void main(String[] args) { Properties props = new Properties(); props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092"); props.put(ProducerConfig.KEY_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName()); props.put(ProducerConfig.VALUE_SERIALIZER_CLASS_CONFIG, StringSerializer.class.getName()); props.put(ProducerConfig.RETRIES_CONFIG, 10); props.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5); props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "false"); // Legacy config Producer<String, String> producer = new KafkaProducer<>(props); // Sending audit logs: producer.send(new ProducerRecord<>("user-audit", "USER_123", "EVENT: CREATED")); producer.send(new ProducerRecord<>("user-audit", "USER_123", "EVENT: UPDATED")); producer.send(new ProducerRecord<>("user-audit", "USER_123", "EVENT: DELETED")); } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Answer to Part A: Kafka guarantees strict ordering ONLY within a single partition. There is NO ordering guarantee across different partitions of the same topic.

Answer to Part B: With max.in.flight.requests.per.connection = 5 and enable.idempotence = false, the producer sends Batch 1 followed immediately by Batch 2 without waiting. If Batch 1 fails due to a temporary network glitch while Batch 2 succeeds, the broker appends Batch 2 first. When the producer retries Batch 1, it lands after Batch 2, reversing chronological order!

Answer to Part C (Deep Probe): Kafka's default partitioner calculates hash(key) % numPartitions. When partitions increase from 6 to 12, the modulo arithmetic produces completely different partition numbers for existing keys. Future events for `USER_123` land on a different partition, permanently shattering chronological consumer ordering!

Correct FixJava
Properties props = new Properties();
props.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
// Fix 1: Enable idempotence. Allows max.in.flight.requests <= 5 while preserving strict order!
props.put(ProducerConfig.ENABLE_IDEMPOTENCE_CONFIG, "true");
props.put(ProducerConfig.MAX_IN_FLIGHT_REQUESTS_PER_CONNECTION, 5);
props.put(ProducerConfig.ACKS_CONFIG, "all");
// Fix 2: Never change topic partition counts if key-based ordering is mandatory.
⚠️ Junior / Unacceptable Response
  • Thinks Kafka guarantees total ordering across the entire topic.
  • Does not understand how network retries flip message batch sequence without idempotence.
🌟 Architect-Level Response
  • Explains in-flight request interleaving and how enable.idempotence=true de-duplicates and orders batches via sequence numbers.
  • Highlights the catastrophic repartitioning trap where changing partition count breaks key-affinity routing.

❓ 2. Question
A consumer group processes image uploads from a Kafka topic. When traffic surges, the consumer group enters an infinite "Rebalance Storm": Consumer instances are repeatedly kicked out of the group, partitions are reassigned every few minutes, and message processing makes zero forward progress.

Part A: Look at the consumer loop in the code snippet. Why is the consumer being evicted from the consumer group?
Part B: What is the difference between session.timeout.ms (heartbeat thread) and max.poll.interval.ms (poll loop)?
Part C (Deep Probe): How does the Cooperative Sticky Assignor (`CooperativeStickyAssignor`) eliminate the "stop-the-world" pause of the legacy Eager Rebalance protocol?
💻 3. Code Challenge
public class ImageProcessingConsumer { public static void main(String[] args) { Properties props = new Properties(); props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092"); props.put(ConsumerConfig.GROUP_ID_CONFIG, "image-processors"); props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, 500); // Pulls 500 records per poll props.put(ConsumerConfig.MAX_POLL_INTERVAL_MS_CONFIG, 300000); // 5 minutes KafkaConsumer<String, byte[]> consumer = new KafkaConsumer<>(props); consumer.subscribe(Collections.singletonList("image-uploads")); while (true) { ConsumerRecords<String, byte[]> records = consumer.poll(Duration.ofMillis(1000)); for (ConsumerRecord<String, byte[]> record : records) { // Takes ~1-2 seconds per image for OCR and thumbnail generation processImageOCR(record.value()); // 500 records * 1.5s = 750 seconds (12.5 minutes)! } consumer.commitSync(); } } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Answer to Part A: The consumer fetched 500 records. At ~1.5s per image, processing the batch takes 12.5 minutes (750 seconds). Because max.poll.interval.ms is set to 5 minutes (300,000ms), the consumer fails to call poll() within the deadline. The Group Coordinator assumes the consumer has locked up or died, kicks it out of the group, and triggers a rebalance. When the consumer finally finishes and calls `poll()`, it is told to re-join, triggering yet another rebalance loop!

Answer to Part B:
• session.timeout.ms: Monitored by a separate background heartbeat thread. Detects if the JVM process crashed or suffered a hard network cut.
• max.poll.interval.ms: Monitored by the main application thread. Detects if the application is stuck in an infinite loop or taking too long between `poll()` invocations.

Answer to Part C (Deep Probe): Under legacy Eager rebalance, ALL consumers revoke ALL their partitions and stop processing (stop-the-world). With Cooperative Sticky Rebalance, consumers only revoke partitions that are actively moving to another member; unaffected partitions continue consuming without interruption.

Correct FixJava
Properties props = new Properties();
props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092");
props.put(ConsumerConfig.GROUP_ID_CONFIG, "image-processors");

// Fix 1: Restrict batch size so batch duration << max.poll.interval.ms
props.put(ConsumerConfig.MAX_POLL_RECORDS_CONFIG, 20); // 20 * 1.5s = 30 seconds

// Fix 2: Increase poll interval headroom
props.put(ConsumerConfig.MAX_POLL_INTERVAL_MS_CONFIG, 180000); // 3 minutes

// Fix 3: Switch from Eager to Cooperative Sticky Rebalance
props.put(ConsumerConfig.PARTITION_ASSIGNMENT_STRATEGY_CONFIG, 
    CooperativeStickyAssignor.class.getName());
⚠️ Junior / Unacceptable Response
  • Suggests increasing session.timeout.ms without realizing heartbeat runs on a separate thread.
  • Does not calculate batch processing time vs max.poll.interval.ms.
🌟 Architect-Level Response
  • Immediately diagnoses max.poll.interval.ms expiration caused by synchronous record processing.
  • Tunes max.poll.records downward or decouples consumption from processing using worker thread pools.
  • Upgrades the partition assignment strategy to CooperativeStickyAssignor.
Offset Management & Delivery Semantics Question 4 of 20
📌 1. Concept Covered
Kafka Offset Commit Mechanics: Risks of enable.auto.commit=true, synchronous vs asynchronous manual commits (`commitSync` vs `commitAsync`), and preventing duplicate processing vs data loss.
❓ 2. Question
An engineer relies on Kafka's default enable.auto.commit = true with auto.commit.interval.ms = 5000. During an unhandled exception or container crash:

Part A: Describe a scenario where auto-commit causes permanent message loss.
Part B: Describe a scenario where auto-commit causes duplicate message processing.
Part C (Deep Probe): Why does combining commitAsync() in the loop with commitSync() in the finally block represent the gold standard for manual offset management?
💻 3. Code Challenge
public class AutoCommitOrderConsumer { public static void main(String[] args) { Properties props = new Properties(); props.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092"); props.put(ConsumerConfig.GROUP_ID_CONFIG, "order-service"); props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "true"); props.put(ConsumerConfig.AUTO_COMMIT_INTERVAL_MS_CONFIG, "5000"); // 5 seconds KafkaConsumer<String, String> consumer = new KafkaConsumer<>(props); consumer.subscribe(Collections.singletonList("orders")); while (true) { ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(100)); for (ConsumerRecord<String, String> record : records) { // If this step throws an unhandled exception or JVM crashes at second 6... insertToDatabase(record.value()); } } } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Answer to Part A (Data Loss): In auto-commit mode, when poll() is called and 5 seconds have elapsed, Kafka automatically commits the highest offset returned by the previous poll. If the worker thread hands records to an internal buffer and crashes before writing them to the database, the broker already has the committed offset! The new consumer resumes from the committed offset, permanently skipping the lost records.

Answer to Part B (Duplicate Processing): If records 1–100 are processed and saved to the database at second 4, but the JVM crashes at second 4.5 before the 5-second auto-commit fires, the offset was never committed to Kafka. When the pod restarts, it re-fetches records 1–100 and inserts them again.

Answer to Part C (Deep Probe): commitAsync() doesn't block the polling loop, maximizing consumer throughput. However, if a transient failure occurs, it should NOT retry (to prevent an older failed offset commit from overwriting a newer successful one). During clean shutdown, commitSync() in the finally block ensures the absolute latest offset is durably acknowledged before releasing partition ownership.

Correct FixJava
Properties props = new Properties();
props.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false"); // Disable auto-commit

try {
    while (running) {
        ConsumerRecords<String, String> records = consumer.poll(Duration.ofMillis(500));
        for (ConsumerRecord<String, String> record : records) {
            processAndSaveToDb(record);
        }
        // Non-blocking commit in main loop
        consumer.commitAsync();
    }
} catch (Exception e) {
    log.error("Consumer loop failure", e);
} finally {
    try {
        // Blocking commit guarantees clean state before shutdown
        consumer.commitSync();
    } finally {
        consumer.close();
    }
}
⚠️ Junior / Unacceptable Response
  • Thinks auto-commit only commits after the developer finishes processing.
  • Does not know why commitAsync() should not retry.
🌟 Architect-Level Response
  • Clearly articulates the timing race conditions between auto-commit intervals and application crashes.
  • Implements manual offset commits with commitAsync() for high throughput and commitSync() for clean shutdown.
  • Understands that Kafka consumer offsets must commit *after* external side effects succeed (At-Least-Once delivery).
Transactional Messaging & EOS Question 5 of 20
📌 1. Concept Covered
Exactly-Once Semantics (EOS) in Kafka: The consume-process-produce loop, transactional.id, atomic multi-partition writes, and consumer isolation.level = read_committed.
❓ 2. Question
A stream processing route consumes raw transactions from input-topic, calculates user account balances, and publishes results to output-topic. The developer configured a transactional producer (`initTransactions()`, `beginTransaction()`, `commitTransaction()`), but downstream consumers still read duplicated and aborted transactions!

Part A: What configuration did the downstream consumer omit that allowed it to read aborted transaction messages?
Part B: How does Kafka's Transaction Coordinator use the two-phase commit protocol and markers (`COMMIT` / `ABORT`) inside the log?
Part C (Deep Probe): How does sendOffsetsToTransaction(...) tie consumer offset commits atomically to producer outputs?
💻 3. Code Challenge
public class TransactionalStreamPipeline { public static void main(String[] args) { Properties prodProps = new Properties(); prodProps.put(ProducerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092"); prodProps.put(ProducerConfig.TRANSACTIONAL_ID_CONFIG, "txn-balance-processor-1"); KafkaProducer<String, String> producer = new KafkaProducer<>(prodProps); producer.initTransactions(); Properties consProps = new Properties(); consProps.put(ConsumerConfig.BOOTSTRAP_SERVERS_CONFIG, "localhost:9092"); consProps.put(ConsumerConfig.GROUP_ID_CONFIG, "balance-consumer-group"); consProps.put(ConsumerConfig.ENABLE_AUTO_COMMIT_CONFIG, "false"); // Downstream consumer configuration missing critical isolation setting! KafkaConsumer<String, String> consumer = new KafkaConsumer<>(consProps); } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Answer to Part A: By default, consumers run with isolation.level = read_uncommitted. In this mode, consumers read all messages immediately, including messages that belong to uncommitted or aborted transactions! Consumers must set isolation.level = read_committed.

Answer to Part B: Kafka writes transactional messages to partition logs immediately with their transactional metadata. When commitTransaction() is invoked, the Transaction Coordinator writes a special Control Marker (`COMMIT` or `ABORT`) to the partition logs. A read_committed consumer stops reading at the Last Stable Offset (LSO) until it encounters the control marker, skipping aborted messages.

Answer to Part C (Deep Probe): producer.sendOffsetsToTransaction(offsets, consumerGroupId) sends the consumer's current offsets to the Transaction Coordinator. The coordinator commits the offsets into the internal __consumer_offsets topic inside the same atomic 2-phase commit as the output messages, guaranteeing that input offsets and output records commit or abort together.

Correct FixJava
// 1. Consumer must specify read_committed:
consProps.put(ConsumerConfig.ISOLATION_LEVEL_CONFIG, "read_committed");

// 2. Consume-Process-Produce atomic loop:
producer.beginTransaction();
try {
    for (ConsumerRecord<String, String> record : records) {
        String result = calculateBalance(record.value());
        producer.send(new ProducerRecord<>("output-topic", record.key(), result));
    }
    // Commit consumer offsets atomically with output records
    Map<TopicPartition, OffsetAndMetadata> offsets = getNextOffsets(records);
    producer.sendOffsetsToTransaction(offsets, consumer.groupMetadata());
    producer.commitTransaction();
} catch (Exception e) {
    producer.abortTransaction();
}
⚠️ Junior / Unacceptable Response
  • Thinks EOS is achieved simply by turning on producer transactions.
  • Has never heard of isolation.level = read_committed.
🌟 Architect-Level Response
  • Explains the role of isolation.level = read_committed and the Last Stable Offset (LSO).
  • Articulates how sendOffsetsToTransaction binds consumer offset commits into the producer's atomic transaction.
  • Understands the internal control markers (`COMMIT`/`ABORT`) written to Kafka logs.

Consumer Lag Triage & Throughput Optimization: Diagnosing lag spikes, the trade-offs between fetch.min.bytes and fetch.max.wait.ms, and decoupling consumer polling from blocking I/O execution.
❓ 2. Question
A Kafka topic with 12 partitions has 12 consumer instances running in a consumer group. During peak business hours, consumer lag steadily balloons by 100,000 messages per hour. Adding more consumer pods does not reduce the lag at all!

Part A: Why does adding 12 more consumer pods (total 24 pods for 12 partitions) fail to increase consumption throughput?
Part B: How do fetch.min.bytes and fetch.max.wait.ms improve throughput for small messages?
Part C (Deep Probe): How can you scale processing concurrency beyond the number of partitions without changing topic partition counts?
💻 3. Code Challenge
public class LaggingOrderConsumer { // Topic: 12 partitions // Consumer Group: 12 consumers active // Symptom: Lag growing rapidly. Ops scaled deployment to 24 pods, but 12 pods sit idle! public void consume() { while (true) { ConsumerRecords<String, Order> records = consumer.poll(Duration.ofMillis(100)); for (ConsumerRecord<String, Order> record : records) { // Each record makes a 150ms HTTP call to legacy payment gateway callPaymentGateway(record.value()); } consumer.commitSync(); } } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Answer to Part A: In a single Kafka consumer group, a partition can only be assigned to at most one consumer instance. With 12 partitions, only 12 consumers can be active simultaneously; the remaining 12 pods sit completely idle, doing zero work.

Answer to Part B: Setting fetch.min.bytes (e.g. 64 KB) and fetch.max.wait.ms (e.g. 500ms) forces the broker to wait until it accumulates substantial data before responding to the consumer. This reduces CPU network syscall overhead and dramatically increases batching efficiency for high-frequency small messages.

Answer to Part C (Deep Probe): Decouple polling from processing using an internal Worker Thread Pool or Java 21 Virtual Threads. The consumer polls records and dispatches tasks to an internal executor pool hashed by key. Offsets are committed once worker tasks complete.

Correct FixJava
public class DecoupledParallelConsumer {
    private final ExecutorService workerPool = Executors.newFixedThreadPool(64);

    public void start() {
        while (running) {
            ConsumerRecords<String, Order> records = consumer.poll(Duration.ofMillis(200));
            // Dispatch records in parallel across worker threads
            List<CompletableFuture<Void>> futures = new ArrayList<>();
            for (ConsumerRecord<String, Order> record : records) {
                futures.add(CompletableFuture.runAsync(() -> callPaymentGateway(record.value()), workerPool));
            }
            // Wait for batch completion before committing offsets
            CompletableFuture.allOf(futures.toArray(new CompletableFuture[0])).join();
            consumer.commitAsync();
        }
    }
}

  • Cannot explain how to scale processing throughput without adding partitions.
🌟 Architect-Level Response
  • Immediately states the 1:1 partition-to-consumer limit per group.
  • Decouples consumer polling from processing using thread pools (or virtual threads).
  • Tunes fetch.min.bytes and compression algorithms to maximize network batch density.
Enterprise Error Handling & Resilience Question 7 of 20

Dead Letter Topic (DLT) & Non-Blocking Retries: Head-of-line blocking problem in standard listener retries, multi-tier retry topics (exponential backoff), and routing poison pills to DLT.
❓ 2. Question
A Spring Boot Kafka listener processes payment notifications. When a transient database deadlock occurs, the listener retries the message 5 times with a 10-second delay between attempts:

Part A: Why does blocking listener retries (`Thread.sleep` or `DefaultErrorHandler` with backoff) cause severe "Head-of-Line Blocking" for all other healthy messages in that partition?
Part B: How does the Non-Blocking Multi-Topic Retry pattern (`orders`, `orders-retry-1`, `orders-retry-2`, `orders-dlt`) resolve head-of-line blocking?
Part C (Deep Probe): How does Spring Kafka's @RetryableTopic configure exponential backoff and DLT routing automatically?
💻 3. Code Challenge
@Component public class PaymentNotificationListener { @KafkaListener(topics = "payments") public void onMessage(ConsumerRecord<String, PaymentEvent> record) throws Exception { int attempts = 0; while (attempts < 5) { try { processPayment(record.value()); return; } catch (TransientDbException e) { attempts++; Thread.sleep(10000); // Blocks partition consumption for 50 seconds! } } throw new RuntimeException("Failed after retries"); } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Answer to Part A: Because Kafka partitions are strictly ordered logs, pausing execution with Thread.sleep() blocks the consumer from polling subsequent messages. Thousands of completely valid messages queued behind the failing message sit frozen, destroying service SLA. Furthermore, long sleeps risk exceeding max.poll.interval.ms, triggering rebalance storms!

Answer to Part B: Instead of sleeping, the failed message is published to a separate retry topic (`payments-retry-1`), and the original partition's offset is immediately committed. The main consumer continues processing subsequent messages without interruption. A dedicated retry listener consumes the retry topic with scheduled delays, escalating to `payments-dlt` if retries exhaust.

Answer to Part C (Deep Probe): In Spring Kafka, annotating the method with @RetryableTopic automatically provisions retry topics, configures exponential backoff, manages header forwarding (`x-original-topic`, `x-exception-message`), and routes permanent failures to `@DltHandler`.

Correct FixJava
@Component
public class PaymentNotificationListener {

    @RetryableTopic(
        attempts = "4",
        backoff = @Backoff(delay = 1000, multiplier = 2.0),
        autoCreateTopics = "true",
        topicSuffixingStrategy = TopicSuffixingStrategy.SUFFIX_WITH_INDEX_VALUE,
        dltStrategy = DltStrategy.FAIL_ON_ERROR
    )
    @KafkaListener(topics = "payments", groupId = "payment-consumer")
    public void onMessage(PaymentEvent payment) {
        processPayment(payment); // Non-blocking: failures publish to payments-retry-X
    }

    @DltHandler
    public void handleDlt(PaymentEvent payment, @Header(KafkaHeaders.RECEIVED_TOPIC) String topic) {
        log.error("Payment landed in DLT after all retries exhausted: {}", payment);
    }
}
⚠️ Junior / Unacceptable Response
  • Advocates putting `Thread.sleep()` in message listeners for retrying.
  • Has no concept of head-of-line blocking across partitions.
🌟 Architect-Level Response
  • Identifies head-of-line blocking and risk of exceeding max.poll.interval.ms.
  • Designs non-blocking retry topic hierarchies with exponential backoff and jitter.
  • Leverages Spring Kafka @RetryableTopic and DLT handlers for automated management.
Data Contracts & Schema Evolution Question 8 of 20
📌 1. Concept Covered
Schema Evolution & Confluent Schema Registry: Avro / Protobuf serialization, Compatibility Modes (Backward, Forward, Full), and avoiding production deserialization crashes during field additions/deletions.
❓ 2. Question
A producer team deploys a new version of their Avro schema for CustomerEvent, adding a new required field loyaltyTier without a default value. Immediately, all existing consumer microservices crash with SerializationException and cannot read any new messages from the topic.

Part A: What is the difference between BACKWARD and FORWARD compatibility in Schema Registry?
Part B: Why did adding a new field without a default value violate BACKWARD compatibility and crash existing consumers?
Part C (Deep Probe): What are the strict rules required to achieve FULL compatibility (both backward and forward)?
💻 3. Code Challenge
// Version 1 Schema { "type": "record", "name": "CustomerEvent", "namespace": "com.company.events", "fields": [ { "name": "customerId", "type": "string" }, { "name": "email", "type": "string" } ] } // Version 2 Schema (Deployed by Producer - Crashes Consumers!) { "type": "record", "name": "CustomerEvent", "namespace": "com.company.events", "fields": [ { "name": "customerId", "type": "string" }, { "name": "email", "type": "string" }, { "name": "loyaltyTier", "type": "string" } // Added without default value! ] }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Answer to Part A:
• BACKWARD (Default): Consumers using the new schema can read data written with the previous schema. Allows upgrading consumers first.
• FORWARD: Consumers using the previous schema can read data written with the new schema. Allows upgrading producers first.

Answer to Part B: When consumers read data produced under the old schema (which lacks `loyaltyTier`), Avro cannot populate the field without a default value and throws a deserialization error. To be backward compatible, any newly added field MUST define a default value (`"default": "STANDARD"` or `"type": ["null", "string"], "default": null`).

Answer to Part C (Deep Probe): FULL Compatibility means schemas are both backward and forward compatible: 1. Only add fields that have default values. 2. Only remove fields that had default values in prior versions. 3. Never rename fields or alter existing field data types.

Correct FixJSON
{
  "type": "record",

Answer Key & Deep-Dive Explanation

Answer to Part A: Spring creates 6 separate KafkaMessageListenerContainer instances. Each container runs its own dedicated thread with its own independent KafkaConsumer instance, joining the consumer group and pulling partitions concurrently.

Answer to Part B:

❓ 2. Question
A service saves an order into a Postgres database and immediately publishes an `OrderCreatedEvent` to Kafka. Under production network spikes, the team discovers phantom events (events in Kafka where no DB record exists) and lost events (DB orders where no Kafka event was ever sent).

Part C (Deep Probe): What is the difference between polling the outbox table vs using Change Data Capture (CDC with Debezium)?
💻 3. Code Challenge
@Service public class OrderService { @Transactional public void createOrder(OrderDto dto) { // Step 1: Save to Postgres orderRepository.save(new Order(dto)); // Step 2: Publish to Kafka within same method // If DB commit fails later -> Ghost event in Kafka! // If Kafka network times out -> DB rolled back or un-sent event! kafkaTemplate.send("orders", dto.getId(), dto); } }
🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Answer to Part A: The Dual-Write problem occurs when updating two independent storage systems (DB and Kafka) without distributed 2PC transactions. There is no atomic guarantee: if Kafka fails, the DB may commit; if the DB commit fails after Kafka sends, phantom events exist in Kafka.

Answer to Part B: In the Transactional Outbox pattern, an outbox table is created in the same database. When an order is saved, an event row is inserted into outbox within the **exact same local ACID database transaction**. Both writes succeed or fail together atomically with 100% certainty.

Answer to Part C (Deep Probe):
• Table Polling: Periodic `SELECT ... FROM outbox` queries introduce latency, DB CPU overhead, and index bloat.
• CDC (Debezium): Reads the database's native transaction log (Postgres WAL / MySQL binlog) directly at the storage engine level. It streams outbox events to Kafka with sub-millisecond latency and near-zero database CPU overhead.

Correct FixJava / Architecture
@Service
public class OrderService {
    @Transactional
    public void createOrder(OrderDto dto) {
        Order order = orderRepository.save(new Order(dto));

        // Atomic write to outbox table within exact same DB transaction!
        OutboxEvent outboxEvent = new OutboxEvent(
            "orders",
            order.getId(),
            "ORDER_CREATED",
            JsonUtils.serialize(order)
        );
        outboxRepository.save(outboxEvent);
        // Debezium CDC tailing Postgres WAL streams outboxEvent to Kafka topic automatically
    }
}

Answer Key & Deep-Dive Explanation

Answer to Part A:
• One-way TLS: Encrypts wire data and validates the broker's identity (client trusts broker). Clients connect anonymously.
• mTLS (Mutual TLS): The broker also requires the client to present a valid X.509 certificate signed by a trusted CA (`ssl.client.auth=required`), authenticating the client's identity before establishing the TCP connection.

Answer to Part B: Kafka extracts the Distinguished Name (DN) from the client certificate (e.g. `CN=payment-service,OU=FinTech,O=Company`). Using ssl.principal.mapping.rules, regex rules extract `payment-service` into the Kafka Principal `User:payment-service`.

Answer to Part C (Deep Probe): Consumers require permissions on BOTH the topic AND the consumer group resource. Grant `READ` on the topic and `READ` on the `Group` resource using `kafka-acls.sh`.

Correct Security ConfigurationBash
# 1. Grant READ permission on the payments topic:
kafka-acls.sh --bootstrap-server broker:9093 --command-config admin.properties \
  --add --allow-principal User:payment-service \
  --operation READ --topic payments

# 2. MANDATORY: Grant READ permission on the consumer group:
kafka-acls.sh --bootstrap-server broker:9093 --command-config admin.properties \
  --add --allow-principal User:payment-service \
  --operation READ --group payment-consumer-group
