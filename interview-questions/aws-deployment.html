🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Part A (The Math of IPv4 Subnets & The 5 Reserved Addresses):
A /28 subnet has $2^{(32 - 28)} = 2^4 = 16$ total IPv4 addresses.
However, AWS reserves exactly 5 IP addresses in every subnet:
1. 10.0.1.0: Network address (first address).
2. 10.0.1.1: Reserved by AWS for the VPC default router.
3. 10.0.1.2: Reserved by AWS for the DNS resolver (AmazonProvidedDNS).
4. 10.0.1.3: Reserved by AWS for future internal use.
5. 10.0.1.15: Network broadcast address (AWS does not support broadcast, but reserves it).
Usable IPs: $16 - 5 =$ only 11 usable IP addresses!

Part B (Why /28 Causes Outages Under Autoscaling):
Each EC2 instance, Application Load Balancer ENI node, RDS endpoint, and Lambda VPC ENI consumes private IP addresses from the subnet.
With only 11 usable IPs, if 2 ALBs and 5 EC2 instances are active, only 4 IPs remain. Any sudden spike in auto-scaling or rolling deployments triggers immediate IP exhaustion, preventing new pods/instances from launching.

Part C (Secondary CIDR Blocks):
While you cannot alter an existing subnet's CIDR boundaries in place, AWS allows you to associate Secondary CIDR blocks (e.g. 100.64.0.0/16 carrier-grade NAT or additional 10.1.0.0/16) to an existing VPC. You can then provision fresh, larger subnets (e.g. /22 with 1,019 usable IPs) without rebuilding the VPC.

Answer Key & Deep-Dive Explanation

Part A (The Circular Routing Deadlock):
In the Terraform snippet, aws_nat_gateway.nat_gw is deployed inside aws_subnet.app_private_subnet.
• A NAT Gateway must always be located inside a PUBLIC subnet that has a direct route to an Internet Gateway (igw).
• Because the NAT Gateway itself is in a private subnet with no path to the Internet, outbound packets loop into the NAT Gateway and die, causing immediate connection timeouts.

Part B (NAT Gateway vs NAT Instance):
• NAT Gateway (AWS Managed): Auto-scales up to 45 Gbps bandwidth, zero OS patching or maintenance, native AWS monitoring, fully managed hardware redundancy. (Cannot attach Security Groups; acts strictly on subnet routing).
• NAT Instance (EC2 based): Limited by EC2 instance size and network burst limits, requires manual script/software patching, requires disabling Source/Destination checks, no automatic failover unless custom failover scripts are deployed.

Part C (Single NAT Gateway Cross-AZ Liabilities):
1. Single Point of Failure: If Availability Zone A suffers an outage, private subnets in AZ B and AZ C completely lose all outbound internet and payment connectivity.
2. Cross-AZ Data Transfer Costs: AWS charges for inter-AZ data transfer ($0.01/GB). Routing gigabytes of outbound API traffic across AZ boundaries significantly inflates cloud bills. Best practice: Deploy one NAT Gateway per Availability Zone.

🎯 Answer Quality:
Not Rated
Answer Key & Deep-Dive Explanation

Part A (Stateless NACLs & Blocked Response Packets):
• Network ACLs are strictly stateless: they do not remember active inbound connections.
• When a client initiates an HTTPS handshake on port 443, the inbound packet is allowed by Rule 100.
• However, the web server's TCP ACK / response packet must be sent back to the client's temporary source port (an ephemeral port).
• Because the outbound NACL rule is configured to DENY all traffic (Rule 100 egress deny), the server's response packet is silently dropped at the subnet boundary. The client times out.

Part B (Ephemeral Ports Specification):
When a client opens an outbound TCP socket to port 443, the client operating system selects an arbitrary high-numbered port from the ephemeral port range:
• Linux kernels / AWS NAT Gateways: 1024 - 65535 (or 32768 - 60999).
To allow return traffic in a stateless NACL, you must configure an outbound rule allowing TCP traffic to destination ports 1024 - 65535 for 0.0.0.0/0.

Part C (Security Groups vs NACLs Comparison Matrix):
• State: Security Groups are stateful (if inbound is allowed, outbound return traffic is automatically allowed regardless of outbound rules). NACLs are stateless.
• Scope: SGs apply at the Elastic Network Interface (ENI / instance) level; NACLs apply at the subnet boundary.
• Rules: SGs only support allow rules; NACLs support both allow and deny rules evaluated in numerical order.

Part A (The Invisible Multipart Upload Leak):
• When uploading files > 100MB via the S3 Multipart Upload API, S3 splits the payload into multiple parts.
• If an upload aborts or disconnects, the uploaded parts remain stored in S3 indefinitely.
• These orphan parts do not appear as objects in standard s3:ListObjectsV2 API calls or console views, but AWS bills them at standard S3 storage rates ($0.023/GB/month). Over months, orphaned multi-part chunks accumulate terabytes of zombie data.

Part B (AbortIncompleteMultipartUpload Lifecycle Rule):

2. Small Object Overhead: Objects < 128KB are never transitioned to infrequent tiers and incur the monitoring fee, making Intelligent-Tiering uneconomical for buckets with millions of tiny thumbnail or JSON files.

Answer Key & Deep-Dive Explanation

Part A (The 3 Phases of Lambda Cold Starts):
1. Init Phase: Spins up Firecracker MicroVM container, initializes Java runtime, downloads deployment package, runs static initializers, loads classpath classes, and constructs handler instance (takes 80% of total cold start time: 4-6 seconds for heavy Spring Boot / Quarkus).
2. Invoke Phase: Executes the handleRequest() handler method.

Part B (How SnapStart & CRaC Work):
• During deployment/version publishing, AWS initializes the function, loads classes, and runs static blocks.
• AWS takes a memory and disk snapshot of the running Firecracker microVM and caches it in a multi-tier cache.
• When a cold start invocation occurs, AWS skips the JVM bootstrap and memory-maps the snapshot directly into RAM in sub-200ms.

Part C (Snapshot Uniqueness & Stale Socket Traps):
1. Broken Cryptographic Uniqueness: Because transactionSalt is initialized in static {}, the exact same random bytes are baked into the snapshot. 1,000 concurrent Lambda instances will share the identical cryptographic salt!
2. Dead Sockets: The TCP connection to PostgreSQL was established during snapshot creation. Upon restoration minutes later, the remote database has timed out the connection, causing SocketException: Broken pipe on invocations.
Fix: Implement CRaC Resource (afterRestore) to reseed randomness and re-establish network sockets.

        this.salt = new byte[32];
        new SecureRandom().nextBytes(this.salt);

    @Override public void beforeCheckpoint(org.crac.Context context) {}

Part A (Why HikariCP Collapses in Serverless):
• In standard container/EC2 deployments, a few long-lived instances share a centralized connection pool.
• In AWS Lambda, each concurrent execution runs in an isolated execution environment.
• If 1,200 Lambda instances spin up, each running HikariCP with maximumPoolSize = 10, Lambda attempts to open $1,200 \times 10 = 12,000$ active TCP connections to PostgreSQL!

Part B (RDS Proxy Multiplexing Architecture):
• RDS Proxy sits between Lambda and Aurora as a managed, highly available proxy layer.
• Lambda functions connect to RDS Proxy via fast local VPC connections.
• RDS Proxy maintains a small, fixed pool of persistent connections (e.g. 50 connections) to the Aurora database and multiplexes (borrows and returns) connections at the individual transaction level.
• If thousands of Lambdas make rapid queries, RDS Proxy queues incoming requests and drains them through the healthy 50 connections without overloading the DB.

1. Using PostgreSQL temporary tables (e.g. CREATE TEMP TABLE ...).
2. Changing session state / transaction isolation level without resetting (e.g. SET search_path, SET TIME ZONE).
3. Prepared statements that are not closed or formatted for proxy caching.

Answer Key & Deep-Dive Explanation

Part A (Scaling Thrashing / Flapping):
This phenomenon is called Scaling Flapping (Thrashing):
• When CPU reaches 70%, the alarm fires and triggers the policy to add 5 instances.
• Because cooldown = 0, the alarm evaluates again on the next 60s period before newly added instances have finished booting and taking load.
• The alarm triggers again and again, scaling capacity up to 40 instances.
• Once all 40 instances boot, aggregate CPU utilization plummets to 5%, triggering an immediate aggressive scale-down back to 4 instances.
• The cycle repeats infinitely, destabilizing the application and driving up EC2 compute costs.

Part B (Target Tracking vs Step Scaling):
• Target Tracking: Works like a home thermostat. You specify the target value (e.g. ALBRequestCountPerTarget = 1000 or CPU = 60%). AWS automatically adds or removes capacity proportional to the deviation. It is the gold standard for ALB request metrics.
• Step Scaling: Applies varying adjustments based on the size of the breach (e.g. +10% if CPU 70-80%, +30% if CPU > 85%).

Part C (Instance Warmup Period):
A Java Spring Boot application can take 60–120 seconds to boot the JVM, warm up JIT, and pass health checks.
The Instance Warmup Period tells the ASG to ignore newly launched instances in metric calculations until the warmup period expires, preventing premature extra scaling actions.

• Geolocation: Routes traffic based strictly on the geographic origin of the user's IP (e.g., all traffic originating from Europe routes to Frankfurt eu-central-1). Geolocation is strictly required to guarantee GDPR compliance and legal data residency constraints.

Part A (The Confused Deputy Attack Scenario):
• SaaS Vendor (Account A) manages customer AWS accounts by assuming an IAM role in each customer's account.
• Customer B configures an IAM role with the trust policy above, allowing Account A to assume it.
• Malicious Customer C signs up for the SaaS service. During setup, Customer C provides Customer B's AWS Role ARN.

• Resource-Based (S3 Bucket Policy): The caller retains their original identity and directly accesses the resource. The principal account does not need to assume a role.

Answer Key & Deep-Dive Explanation

Part A (Account-Wide Concurrency Exhaustion):
• AWS accounts have a default regional concurrency limit of 1,000 concurrent executions shared across all Lambda functions in the region.
• Functions without explicit configuration draw from the Unreserved Concurrency Pool.
• If a background ETL or batch job scales to 1,000 executions, it completely drains the unreserved pool.
• Any other function in the account (even a critical 10ms payment API) cannot allocate execution slots and is immediately throttled with HTTP 429 Rate Exceeded.

Part B (Reserved Concurrency: Floor & Ceiling):
• Allocating reserved_concurrent_executions = 200 achieves two things:
1. Guaranteed Floor: 200 execution slots are dedicated strictly to this function; other functions cannot steal them.
2. Strict Ceiling: The function can never scale beyond 200 executions, preventing it from consuming the rest of the account's unreserved pool.
Note: AWS requires at least 100 concurrency units to remain in the unreserved pool.

Part C (Provisioned Concurrency):
• Reserved Concurrency allocates slots, but instances still suffer initial cold starts upon invocation.
• Provisioned Concurrency: AWS pre-initializes the execution environment, boots the JVM, and loads classes in advance. Functions respond in sub-10ms with zero cold starts. It is billed per GB-second of provisioned uptime.
