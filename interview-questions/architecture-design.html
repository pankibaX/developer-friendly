Answer Key & Deep-Dive Explanation

Part A (The LSP Violation & Broken Polymorphism):
• The Liskov Substitution Principle states: "Objects of a superclass shall be replaceable with objects of its subclasses without breaking the application."
• Any client code operating on BankAccount account expects that calling account.withdraw(...) is a valid contract operation.
• Substituting a FixedTermDepositAccount throws an unexpected runtime exception (UnsupportedOperationException), crashing batch transfer services and violating client expectations.

Part B (Design-by-Contract LSP Rules):
1. Preconditions cannot be strengthened in a subtype (you cannot require stricter constraints than the parent).
2. Postconditions cannot be weakened in a subtype (you cannot guarantee less than the parent).
3. Exception covariance: Subtypes may not throw new checked exceptions unless they are subtypes of exceptions declared by the parent method.

Checking accounts implement both; Fixed Term accounts implement only DepositCapable. The withdrawal service accepts Withdrawable, making runtime type errors mathematically impossible at compile time.

Answer Key & Deep-Dive Explanation

Part A (Near-Cache Invalidation Mechanics):
• Near-Cache stores a copy of frequently read entries in the local JVM memory of the calling node to avoid network round-trips to the owner node.
• In the configuration snippet: <invalidate-on-change>false</invalidate-on-change>!
• When Node 1 mutates the seat status in the distributed map, it does not broadcast an invalidation event.
• Node 3 continues reading its local Near-Cache copy for 120 seconds until TTL expires, serving stale, corrupted availability.
Fix: Set invalidate-on-change to true. When an entry is updated, Hazelcast broadcasts an invalidation event to all cluster Near-Caches.

Part B (Cache Stampede & Mutex Loading):
• When a high-traffic key (e.g. Flight 101 seat map) expires, thousands of concurrent threads experience a simultaneous cache miss.
• All 10,000 threads hit the primary relational database at the exact same millisecond, exhausting database connection pools and crashing the DB.
• Fix: Use Hazelcast MapLoader with mutual exclusion or atomic locking so only one worker thread executes the DB query while the other 9,999 threads await the repopulated cache.

Part C (Split-Brain & Quorum Protection):
• If a network partition splits a 4-node cluster into two isolated 2-node partitions, both sides believe the other is dead.
• Without protection, both sub-clusters elect masters and accept independent writes, causing irreconcilable data divergence.
• Quorum Protection: Requires a minimum number of participating nodes (e.g. $\lfloor N/2 \rfloor + 1 = 3$ nodes) to accept writes. The 2-node sub-cluster drops into read-only mode, eliminating split-brain corruption.

Answer Key & Deep-Dive Explanation

Part A (Why Partition Tolerance Is Non-Negotiable):
• In distributed systems operating across networks, routers reboot, fiber cables are cut, and switches drop packets.
• Network partitions ($P$) will inevitably occur.
• You cannot "choose" CA. When a partition occurs, the system must either:
1. Cancel the operation to preserve data consistency → CP (sacrificing Availability).
2. Proceed with local data to preserve uptime → AP (sacrificing Consistency).

Part B (CP vs AP in Banking Cash Withdrawals):
• CP Selection: The ATM queries the local node. Because it cannot reach the remote master to acquire a synchronous lock, the ATM displays: "Network error: Transaction declined. Please try again later." (Preserves balance consistency; zero risk of overdraft; poor customer experience).
• AP Selection: The ATM dispenses the $500 based on the last known cached balance.
Business Risk: The customer's accomplice can withdraw $500 simultaneously at an ATM in Data Center A! When the partition heals, the account is overdrawn by $1,000. Real banks use a bounded AP model (allow up to $200 emergency offline limit).

Part C (The PACELC Theorem):
CAP only describes behavior during a partition. PACELC states:
If there is a Partition ($P$), choose between Availability ($A$) and Consistency ($C$);
Else ($E$), choose between Latency ($L$) and Consistency ($C$).
In healthy normal operations, replicating synchronously across data centers adds 80ms latency (Consistency), while replicating asynchronously responds in 2ms (Low Latency).

Answer Key & Deep-Dive Explanation

Part A (The Pitfalls of Lock-Based Queues):
• ArrayBlockingQueue uses ReentrantLock and condition variables.
• When a lock cannot be acquired, the operating system suspends the thread, triggering an expensive Kernel Context Switch (costing 1,000–5,000 CPU cycles).
• Multiple CPU cores contend for the same memory address (head and tail pointers), causing Cache-Line Bouncing across CPU L1/L2 caches (MESI invalidations).

Part B (How the LMAX Disruptor Works):
1. Pre-allocated Circular Ring Buffer: Avoids GC allocation overhead entirely during runtime. Buffer size is a power of 2, allowing fast bitwise modulo operations (sequence & (bufferSize - 1)).
2. Lock-Free Sequences: Uses monotonic atomic sequence numbers. Producers claim slots via lock-free CAS; consumers poll sequences without locks.
3. Single-Writer Principle: When configured with a single writer thread, CAS is completely eliminated, running at raw memory bus speed.

Part C (False Sharing & Cache-Line Padding):
• Modern CPUs read memory in 64-byte Cache Lines.

    private final int numberOfReplicas; // Virtual nodes per physical node
    private final SortedMap<Integer, T> circle = new TreeMap<>();

        if (!circle.containsKey(hash)) {

        }

    }

Part A (Amdahl's Law & The Limits of Scaling):
• Amdahl's Law states: $S_{\text{latency}} = \frac{1}{(1 - p) + \frac{p}{s}}$, where $p$ is the parallelizable portion of code.
• If a bottleneck is caused by a shared resource (database row locks, connection pool exhaustion, or synchronized blocks), adding more instances does not reduce latency.
• In fact, adding 16 more instances will increase database connection contention and context switching, degrading performance even further!

Part B (Interpreting CPU FlameGraphs):
• Horizontal Width: Represents the percentage of CPU time spent in that method and its children (wider frame = more CPU consumed).
• Vertical Axis: Represents the call stack depth (the top of the stack is the method currently executing on the CPU).
• Look for wide "plateaus" at the top of the graph: these are your primary CPU hot spots.

Part C (Regex Compilation State Machine Bottleneck):
• Pattern.compile() compiles the regex string into an internal Non-deterministic Finite Automaton (NFA) state machine, creating thousands of objects and consuming heavy CPU cycles.
• Compiling it 15,000 times per second wastes 75% of server CPU.
• Fix: Pattern is thread-safe! Compile it once into a private static final Pattern constant.
