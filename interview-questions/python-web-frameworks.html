Answer Key & Deep-Dive Explanation
1. select_related vs prefetch_related:
• select_related() creates a single complex SQL query with an INNER JOIN or LEFT OUTER JOIN. It is valid only for single-valued relationships (ForeignKey forward lookup and OneToOneField). • prefetch_related() executes a separate query for each relationship using WHERE id IN (...) and joins the objects in Python memory via QuerySet._result_cache.

2. Optimized 2-Query Architecture:
from django.db.models import Prefetch

def get_recent_orders_report_optimized() -> List[Dict[str, Any]]:
    # Query 1: Fetch Orders + Customers via SQL JOIN
    # Query 2: Fetch OrderItems + Products via IN clause
    orders = Order.objects.select_related('customer').prefetch_related(
        Prefetch(
            'items',
            queryset=OrderItem.objects.select_related('product')
        )
    ).order_by('-created_at')[:100]

    report = []
    for o in orders:
        report.append({
            "order_id": o.id,
            "customer_name": o.customer.name, # Cached in memory from SQL JOIN
            "items": [
                {"product": item.product.title, "qty": item.quantity} # Cached from Prefetch!
                for item in o.items.all()
            ]
        })
    return report

Answer Key & Deep-Dive Explanation
1. Why @transaction.atomic Fails Here:
@transaction.atomic creates a database transaction boundary (BEGIN ... COMMIT). However, under the default READ COMMITTED isolation level, Transaction A and Transaction B can both execute SELECT balance FROM wallet concurrently. Both inspect balance = 100 >= 100, both compute 100 - 100 = 0 in Python memory, and both write UPDATE wallet SET balance = 0, resulting in the user withdrawing $200 instead of $100.

2. Solution 1: Pessimistic Row Locking (select_for_update):
from django.db import transaction
from decimal import Decimal

class WalletService:
    @staticmethod
    @transaction.atomic
    def debit_wallet(user_id: str, amount: Decimal) -> bool:
        # Issues SELECT ... FOR UPDATE: locks row until transaction commits
        wallet = Wallet.objects.select_for_update().get(user_id=user_id)
        if wallet.balance >= amount:
            wallet.balance -= amount
            wallet.save()
            return True
        return False

3. Solution 2: Atomic Database-Level F() Update (High Throughput):
from django.db.models import F

def debit_wallet_atomic_f(user_id: str, amount: Decimal) -> bool:
    # Single atomic query executed inside the database engine:
    # UPDATE wallet SET balance = balance - 100 WHERE user_id = 'x' AND balance >= 100
    rows_updated = Wallet.objects.filter(
        user_id=user_id,
        balance__gte=amount
    ).update(balance=F('balance') - amount)
    
    return rows_updated > 0

2. Dual Sync/Async Compatible Middleware (Django 3.1+ / 4+ / 5+):
from django.utils.decorators import sync_and_async_middleware
from asgiref.sync import iscoroutinefunction
from django.http import HttpRequest, HttpResponse
from typing import Callable

@sync_and_async_middleware
class TenantAuditMiddleware:
    sync_capable = True
    async_capable = True

    def __init__(self, get_response: Callable):
        self.get_response = get_response
        self._is_async = iscoroutinefunction(get_response)

    def __call__(self, request: HttpRequest) -> HttpResponse:
        if self._is_async:
            return self.__acall__(request)
            
        # Synchronous execution path
        tenant_id = request.headers.get("X-Tenant-ID", "PUBLIC")
        request.tenant_id = tenant_id
        response = self.get_response(request)
        response["X-Tenant-Resolved"] = tenant_id
        return response

    async def __acall__(self, request: HttpRequest) -> HttpResponse:
        # Asynchronous execution path (zero thread switching!)
        tenant_id = request.headers.get("X-Tenant-ID", "PUBLIC")
        request.tenant_id = tenant_id
        response = await self.get_response(request)
        response["X-Tenant-Resolved"] = tenant_id
        return response

Answer Key & Deep-Dive Explanation
1. The Signal-Transaction Race Condition:
post_save fires as soon as Order.objects.create() executes the SQL INSERT statement. However, because the view is wrapped in @transaction.atomic, the changes are not yet committed to PostgreSQL. The Celery task is published to RabbitMQ/Redis immediately. A distributed Celery worker picks up the task within 2 milliseconds and executes Order.objects.get(id=order_id). Because PostgreSQL uses Multi-Version Concurrency Control (MVCC), uncommitted rows are invisible to other connections. The worker crashes with Order.DoesNotExist.

2. Production Solution with transaction.on_commit():
from django.db import transaction
from django.db.models.signals import post_save
from django.dispatch import receiver

@receiver(post_save, sender=Order)
def on_order_created(sender, instance, created, **kwargs):
    if created:
        # Enqueue execution ONLY after the outer transaction successfully COMMITS
        transaction.on_commit(
            lambda: generate_shipping_label_task.delay(instance.id)
        )

3. Architectural Best Practice:
Signals obscure control flow (spaghetti callbacks) and make unit testing difficult. Prefer explicit service-layer orchestration: 
def create_order_service(cart_data) -> Order:
    with transaction.atomic():
        order = Order.objects.create(...)
        charge_payment(order)
        transaction.on_commit(lambda: generate_shipping_label_task.delay(order.id))
    return order

from django.core.cache import cache
import time

def get_dashboard_metrics_safe(tenant_id: str) -> dict:
    cache_key = f"saas:tenant:{tenant_id}:dashboard:v1"
    data = cache.get(cache_key)
    if data is not None:
        return data

    # Acquire distributed lock: Only ONE worker rebuilds the cache!
    lock_key = f"lock:{cache_key}"
    with cache.lock(lock_key, timeout=15):
        # Double-check: Another worker may have filled the cache while we waited for lock
        data = cache.get(cache_key)
        if data is not None:
            return data

        # Execute expensive database query
        data = execute_heavy_database_aggregation(tenant_id)
        cache.set(cache_key, data, timeout=300)

    return data

Answer Key & Deep-Dive Explanation
1. Why Reverse Proxies Mask Client Identity:
In production, SSL is terminated at the load balancer (AWS ALB / Cloudflare). The load balancer opens a fresh TCP connection to Flask over plain HTTP. Flask's WSGI server sees the incoming TCP connection originating from the load balancer's private IP (10.0.x.x) and receives wsgi.url_scheme = 'http'.

2. The IP Spoofing Threat:
An attacker can send an arbitrary HTTP header: X-Forwarded-For: 192.168.1.1. The load balancer appends the real IP to the end: X-Forwarded-For: 192.168.1.1, 203.0.113.195. If application code blindly takes the first comma-separated value, the attacker successfully spoofs an internal IP, bypassing rate limiters and IP firewalls.

3. Secure ProxyFix Configuration:

    app.wsgi_app,
    x_for=1,    # Trust exactly 1 upstream proxy for REMOTE_ADDR
    x_proto=1,  # Trust exactly 1 upstream proxy for wsgi.url_scheme (https)
    x_host=1,   # Trust exactly 1 upstream proxy for Host header
    x_port=1
)
